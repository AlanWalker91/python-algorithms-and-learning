## 一、测试基础

**1. 软件测试的目的是什么？**
发现软件中的缺陷，验证软件是否满足需求，评估软件质量，降低发布风险。测试不能证明软件无缺陷，只能证明缺陷存在。

**2. 黑盒测试和白盒测试的区别？**
- 黑盒：不关注内部实现，基于需求/输入输出设计用例（等价类、边界值、因果图等）。
- 白盒：基于代码逻辑设计用例（语句覆盖、判定覆盖、条件覆盖、路径覆盖）。
- 灰盒：介于两者之间，既了解部分内部结构又基于功能设计用例。

**3. 常用的黑盒测试用例设计方法？**
等价类划分、边界值分析、因果图、判定表、正交实验法、错误推测法、场景法、状态迁移法。

**4. 白盒测试的覆盖率有哪些？（由弱到强）**
语句覆盖 < 判定覆盖 < 条件覆盖 < 判定/条件覆盖 < 条件组合覆盖 < 路径覆盖。

**5. 描述一个完整的测试流程。**
需求分析 → 制定测试计划 → 设计测试用例 → 用例评审 → 搭建环境 → 执行测试 → 提交缺陷 → 回归测试 → 输出测试报告 → 上线验证。

**6. 一个 Bug 的生命周期？**
New → Assigned → Open(处理中) → Fixed → 回归验证 → Closed；若未修复复现则 Reopen；无法复现/非缺陷可 Rejected。

**7. 缺陷等级怎么划分？**
- 致命(Blocker)：系统崩溃、主流程不可用、数据丢失。
- 严重(Critical)：主要功能失效但有临时方案。
- 一般(Major)：次要功能问题。
- 轻微(Minor)：界面、文案、体验问题。

**8. 一个完整的缺陷报告应包含哪些内容？**
标题、缺陷ID、模块、环境（系统/浏览器/版本）、前置条件、复现步骤、预期结果、实际结果、优先级、严重程度、截图/日志/录屏、指派人。

**9. 优先级(Priority)和严重程度(Severity)的区别？**
- 严重程度：缺陷对系统的破坏程度（客观）。
- 优先级：缺陷修复的紧急程度（主观，结合业务）。
- 二者不完全一致：如首页 Logo 打错，严重程度低但优先级高。

**10. 开发说这不是 Bug，怎么办？**
先确认需求文档/PRD，若与需求一致则是 Bug；无明确需求则拉上产品确认；提供复现步骤、日志、截图等证据，用数据说话而非争论。

**11. α测试和β测试的区别？**
- α测试：开发方在受控环境下由用户/测试人员进行的测试。
- β测试：真实用户在实际环境中进行的测试，开发方不可控。

**12. 冒烟测试、回归测试、系统测试的区别？**
- 冒烟测试：验证核心主流程是否通畅，决定是否进入详细测试。
- 回归测试：修改代码后验证原有功能未被破坏。
- 系统测试：对整个系统进行完整功能与非功能测试。

## 二、功能测试

**13. 如何测试一个登录功能？**
- 正常：正确账号密码登录成功。
- 异常：错误密码/账号、空账号、空密码、账号不存在的提示。
- 边界：账号/密码超长、超短、特殊字符、SQL注入、XSS。
- 安全：密码加密传输、密码框密文显示、连续失败锁定、验证码逻辑。
- 会话：记住密码、Token/Session 有效期、多端登录、退出后 Session 失效。
- 兼容：不同浏览器、不同分辨率。
- UI：布局、提示文案、按钮状态。

**14. 如何测试一个搜索框？**
- 功能：关键词精确/模糊搜索、无结果提示、结果准确性、结果排序。
- 边界：空输入、超长输入、纯空格、特殊字符、SQL注入、Emoji。
- 交互：回车触发、点击搜索、历史记录、联想提示、清空按钮。
- 性能：大数据量搜索响应时间、高并发。
- 兼容：中英文、大小写、繁简体。

**15. 如何测试一个文件上传功能？**
- 文件类型：允许类型能传、禁止类型被拦截、无后缀、伪造后缀。
- 文件大小：0字节、正常、超过上限、临界值。
- 文件数量：单个、批量、超过数量限制。
- 异常：上传中断网、重复上传、同名文件、中文/特殊字符文件名。
- 安全：上传可执行文件/木马、路径穿越、内容与后缀不符。
- 交互：进度条、取消、失败重试、成功提示。

**16. 如何测试支付功能？**
- 正常支付：各种支付方式（微信/支付宝/银行卡）成功。
- 金额：0元、最小金额、最大金额、小数位、负数。
- 异常：余额不足、支付超时、网络中断、重复支付、并发支付。
- 状态：支付中/成功/失败/退款状态流转正确。
- 安全：金额篡改（改前端价格）、越权支付他人订单、幂等性。
- 对账：订单与支付金额一致、退款金额正确。

**17. 如何设计一个购物车的测试用例？**
- 添加：添加商品、添加已下架商品、库存不足、加入数量超库存。
- 修改：增减数量、数量为0、删除商品、清空购物车。
- 计算：单品总价、多品合计、优惠券/满减、运费计算准确。
- 状态：商品价格变动、失效商品提示、勾选/取消勾选。
- 边界：购物车上限、同一商品多次添加合并。
- 并发：多端同时操作同一账号购物车。

**18. 需求评审时你会关注什么？**
需求是否完整、明确、可测试；逻辑是否自洽；异常场景是否覆盖；边界是否定义；与现有功能是否冲突；性能/兼容/安全要求是否明确；验收标准是否清晰。

**19. 需求文档不完善，如何开展测试？**
参考同类竞品、历史版本、原型图、UI 设计稿；与产品/开发沟通确认；基于经验做探索性测试；用假设列表让相关方确认；记录不明确点作为风险上报。

**20. 什么是探索性测试？**
一种边学习、边设计、边执行的测试方法，不依赖预先写好的用例，测试人员根据对系统的理解动态调整测试策略，适合需求不明确或时间紧的场景。

**21. 测试用例的粒度如何把控？**
核心/复杂功能用例细化，简单功能可合并；保证覆盖主流程、异常流、边界；避免用例重复冗余；结合风险等级分配测试深度。

**22. 如何减少漏测？**
需求评审阶段深度介入、用例评审、覆盖率度量、探索性测试补充、Bug 复盘分析漏测原因、建立缺陷知识库、加强边界与异常场景设计。

## 三、自动化测试

**23. 测试开发和普通功能测试的区别？**
测试开发不仅执行测试，更侧重开发测试工具、平台、自动化框架、CI/CD 集成，提升测试效率，需要较强的编码能力（Python/Java/Go）。

**24. 什么样的项目/功能适合做自动化测试？**
需求稳定、迭代周期长、回归频繁、手工重复度高、核心业务流程、接口稳定的模块。不适合：需求频繁变动、一次性项目、UI 频繁改动、探索性/易用性测试。

**25. 自动化测试的分层（金字塔模型）？**
- 底层：单元测试（数量最多、成本最低、最稳定）。
- 中层：接口/集成测试（性价比最高，推荐重点投入）。
- 顶层：UI 测试（数量最少、成本最高、最不稳定）。
理念：越底层测试越多，越顶层越少。

**26. 常用的自动化测试框架有哪些？**
- 接口：Requests + Pytest/JUnit、RestAssured、HttpRunner、Postman/Newman。
- Web UI：Selenium、Playwright、Cypress、WebDriverIO。
- 移动端：Appium、UIAutomator2、XCUITest。
- 单元测试：JUnit、TestNG、pytest、unittest。

**27. Selenium 中的三种等待方式？**
- 强制等待：`time.sleep()`，固定死等，不推荐。
- 隐式等待：`implicitly_wait(10)`，全局生效，找不到元素时轮询。
- 显式等待：`WebDriverWait + expected_conditions`，针对特定条件，最灵活，最推荐。

**28. Selenium 定位元素有哪些方式？如何提高稳定性？**
定位方式：id、name、class_name、tag_name、link_text、partial_link_text、xpath、css_selector。
提高稳定性：优先用 id/唯一属性；避免绝对路径 XPath；用相对定位；结合显式等待；避免依赖动态生成的属性。

**29. 显式等待和隐式等待能混用吗？**
不推荐混用。混用可能导致等待时间叠加、行为不可预测（实际等待时间可能超过设定值）。建议统一使用显式等待。

**30. 什么是 PO（Page Object）设计模式？有什么好处？**
将页面元素定位和操作封装成独立的 Page 类，测试用例只调用页面方法，实现"测试逻辑"与"页面元素"分离。
好处：页面变动只需改对应 Page 类、代码复用高、可维护性强、可读性好。

**31. 如何处理自动化中的元素定位不到 / 元素不稳定？**
- 加显式等待，确保元素可见/可点击。
- 检查是否在 iframe 内（需切换 frame）。
- 检查是否是动态 id（用其他稳定属性）。
- 检查是否有弹窗遮挡。
- 滚动到元素可见区域。
- 检查是否是新窗口/标签页（需切换 handle）。

**32. 如何处理弹窗、iframe、多窗口？**
- 弹窗(alert)：`driver.switch_to.alert.accept()/dismiss()`。
- iframe：`driver.switch_to.frame()`，操作完 `switch_to.default_content()`。
- 多窗口：`driver.window_handles` 获取句柄列表，`switch_to.window(handle)` 切换。

**33. 自动化测试如何做数据驱动？**
用 `@pytest.mark.parametrize` 参数化，或读取外部文件（Excel/CSV/YAML/JSON/数据库），将测试数据与代码分离，一套逻辑跑多组数据，提高用例复用性。

**34. pytest 常用的功能有哪些？**
- Fixture：前置/后置管理，`@pytest.fixture`，支持 scope。
- 参数化：`@pytest.mark.parametrize`。
- 标记：`@pytest.mark.smoke` 分组执行。
- 断言：直接用 assert，失败信息友好。
- 插件：pytest-html（报告）、pytest-xdist（并行）、pytest-rerunfailures（失败重跑）、allure-pytest（Allure报告）。
- conftest.py：共享 fixture 和配置。

**35. 什么是 fixture？和 setup/teardown 的区别？**
fixture 是 pytest 提供的前置/后置资源管理机制，比传统 setup/teardown 更灵活：可指定作用域(function/class/module/session)、可参数化、可相互依赖、可通过 yield 实现清理。

**36. 自动化测试用例执行失败怎么排查？**
先看是脚本问题还是真实 Bug；查看日志、截图、报错堆栈；本地复现；检查是否环境/数据/网络问题；检查是否元素定位失效；确认是否偶发（失败重跑）。

**37. 如何保证自动化用例的稳定性（减少 Flaky Test）？**
使用显式等待代替固定等待；测试数据独立、每次自动初始化和清理；用例间无依赖；避免依赖执行顺序；隔离环境；失败自动重试；定期维护失效用例。

**38. 自动化测试脚本如何管理测试数据？**
- 独立的数据准备与清理（每个用例自建自销）。
- 使用工厂/构造方法生成数据。
- 数据与脚本分离（配置文件/数据库）。
- 使用测试专用账号/环境，避免污染生产数据。

**39. 什么是持续集成(CI)？自动化如何接入 CI/CD？**
CI 是频繁将代码集成到主干并自动构建、测试的实践。自动化接入：代码提交触发 Jenkins/GitLab CI/GitHub Actions → 自动拉代码、构建、部署测试环境 → 运行自动化用例 → 生成报告 → 结果通知（邮件/钉钉/企业微信）。

**40. 如何评估自动化测试的收益/效果？**
用例覆盖率、执行通过率、缺陷发现率、回归节省的人力工时、维护成本、用例稳定性(Flaky率)、执行时长。收益 = 手工成本 - 自动化开发与维护成本。

**41. 接口自动化和 UI 自动化的区别？各自优缺点？**
- 接口自动化：直接测接口，快、稳定、维护成本低，但不能测 UI 展现。
- UI 自动化：模拟真实用户操作，覆盖端到端，但慢、脆弱、维护成本高。
- 实践中优先做接口自动化，UI 自动化只覆盖核心流程。

**42. Selenium 和 Playwright 的区别？**
- Playwright：自带自动等待、跨浏览器（Chromium/Firefox/WebKit）、支持多语言、并发能力强、API 更现代、无需额外驱动。
- Selenium：生态成熟、社区大、需管理 driver、需手动处理等待。
- Playwright 在稳定性和易用性上更优，Selenium 生态更广。

**43. 如何设计一个自动化测试框架？**
分层结构：用例层 + 业务/关键字层 + 页面对象层 + 工具层（请求封装、日志、断言、数据处理）+ 配置层 + 报告层。
核心组件：数据驱动、日志、报告(Allure)、失败重试、CI 集成、异常处理、环境配置管理。

## 四、接口测试

**44. 什么是接口测试？为什么要做接口测试？**
接口测试是对系统组件间接口进行的测试，验证接口的功能、逻辑、数据、异常处理是否正确。
原因：比 UI 测试更早介入（前后端并行）、更稳定、更快、能覆盖 UI 难以触发的异常场景、性价比高。

**45. 接口测试主要测试哪些内容？**
- 功能：请求方法、URL、参数、返回状态码、响应字段与数据类型、业务逻辑正确性。
- 异常：参数缺失、类型错误、超长、非法值、越权。
- 安全：鉴权、越权、SQL注入、敏感信息加密。
- 性能：响应时间、并发。
- 其他：幂等性、事务、数据一致性。

**46. GET 和 POST 的区别？**
GET 参数在 URL、有长度限制、可缓存、幂等、用于查询；POST 参数在 body、无明显长度限制、不缓存、非幂等、用于提交/修改，相对更安全。

**47. 常见的 HTTP 状态码？**
200 成功、201 创建成功、301/302 重定向、304 未修改、400 参数错误、401 未认证、403 无权限、404 未找到、405 方法不允许、500 服务器错误、502 网关错误、503 服务不可用、504 网关超时。

**48. Cookie 和 Session 的区别？**
- Cookie：存储在客户端浏览器，有大小限制，可被篡改。
- Session：存储在服务端，通过 SessionID（常存于 Cookie）关联，更安全。
- Token(JWT)：无状态，服务端不存储，适合分布式/前后端分离。

**49. 接口测试中如何处理接口依赖（如登录后才能操作）？**
先调用前置接口获取数据（如登录拿 Token），提取响应中的关键字段（关联/参数传递），再传给后续接口。工具中用变量提取（JSONPath/正则），代码中用变量传递或 fixture。

**50. 如何做接口关联/参数化？**
- 关联：从上一个接口响应中提取字段（JSONPath、正则、Header），作为下一个接口的入参。
- 参数化：将变化的数据抽离到外部文件或参数列表，一套脚本多组数据执行。

**51. 常用的接口测试工具？**
- 手工/半自动：Postman、Apifox、JMeter、SoapUI。
- 代码框架：Requests+Pytest、RestAssured、HttpRunner。
- 抓包：Charles、Fiddler、Wireshark、mitmproxy。

**52. 如何进行接口鉴权测试？常见鉴权方式？**
鉴权方式：Basic Auth、API Key、Token/JWT、OAuth2.0、签名验签。
测试点：无 Token 访问、错误/过期 Token、Token 越权访问他人数据、越权访问高权限接口、Token 可否伪造。

**53. 接口幂等性是什么？如何测试？**
幂等：同一请求多次执行结果一致，不会重复产生副作用（如重复支付、重复下单）。
测试：用相同参数多次调用接口，验证只生效一次（常通过唯一订单号/token 保证）。

**54. 如何测试一个"用户注册"接口？**
- 正常：合法参数注册成功。
- 参数：必填缺失、类型错误、超长、特殊字符、格式校验（手机号/邮箱/密码强度）。
- 业务：重复注册（用户名/手机号已存在）、验证码校验、并发注册同一账号。
- 安全：SQL注入、XSS、密码是否加密存储、敏感信息返回。
- 返回：状态码、错误码、提示信息是否正确。

**55. RESTful API 有什么特点？**
- 用 URL 定位资源，用 HTTP 方法表达操作（GET查/POST增/PUT改/DELETE删）。
- 无状态。
- 返回统一格式（常为 JSON）。
- 使用标准状态码。
- 资源名用名词、复数。

**56. 如何 mock 接口？为什么要 mock？**
Mock 是模拟真实接口返回预设数据。原因：依赖的接口未开发完成、第三方接口不稳定/收费、构造异常场景困难、并行开发。
工具：Postman Mock、Moco、WireMock、mockjs、unittest.mock。

## 五、性能测试

**57. 什么是性能测试？和功能测试的区别？**
性能测试验证系统在特定负载下的响应时间、吞吐量、资源占用等指标是否满足要求；功能测试关注"能不能用"，性能测试关注"用得好不好、扛不扛得住"。

**58. 性能测试的分类？**
- 负载测试：逐步加压，找系统在满足指标下能承受的最大负载。
- 压力测试：持续加压直到系统崩溃，找系统瓶颈/极限。
- 并发测试：多用户同时操作，测并发处理能力和数据一致性。
- 稳定性测试(疲劳测试)：长时间运行，看是否有内存泄漏、性能衰减。
- 容量测试：确定系统最大数据/用户容量。
- 基准测试：单用户下的性能基线。

**59. 性能测试的核心指标有哪些？**
- 响应时间(RT)：请求到响应的耗时。
- 吞吐量(TPS/QPS)：每秒事务数/查询数。
- 并发用户数：同时向服务器发请求的用户数。
- 错误率：失败请求占比。
- 资源利用率：CPU、内存、磁盘 I/O、网络、带宽。
- PV/UV：页面访问量/独立访客数。

**60. TPS、QPS、RT、并发数的关系？**
- 通用公式：并发数 ≈ TPS × 平均响应时间(RT)。
- TPS = 并发数 / RT。
- RT 越小、并发越大，TPS 越高，达到瓶颈后 TPS 不再增长甚至下降。

**61. 常用的性能测试工具？**
- JMeter（开源、功能全、社区大，最常用）。
- LoadRunner（商业、功能强大）。
- Locust（Python 编写脚本、易扩展）。
- Gatling（Scala、高性能）。
- wrk / ab（轻量命令行压测）。

**62. JMeter 的核心组件有哪些？**
- 线程组(Thread Group)：模拟并发用户。
- 取样器(Sampler)：发送请求（HTTP/JDBC等）。
- 逻辑控制器：控制执行逻辑（循环、条件）。
- 配置元件：CSV数据、HTTP默认值、Cookie管理。
- 定时器：控制请求间隔（模拟真实用户）。
- 断言：验证响应正确性。
- 监听器：查看结果（聚合报告、结果树）。
- 前置/后置处理器：参数提取、关联。

**63. 如何设计一个性能测试方案？**
明确测试目标和指标 → 分析业务模型（核心场景、比例）→ 设计场景（并发数、加压方式、持续时间）→ 准备测试数据和环境（尽量接近生产）→ 编写脚本 → 执行并监控 → 分析结果定位瓶颈 → 优化后回归 → 输出报告。

**64. 性能测试如何定位瓶颈？**
从前到后逐层排查：
- 客户端/压测机是否成为瓶颈（自身 CPU/带宽打满）。
- 网络：带宽、延迟。
- 应用层：线程池、连接池、代码算法、GC、锁。
- 中间件：Web 服务器、缓存配置。
- 数据库：慢 SQL、索引、锁、连接数。
- 硬件资源：CPU、内存、磁盘 I/O。
借助 APM 工具（SkyWalking、Arthas、top、jstack、慢查询日志）分析。

**65. 响应时间慢，可能的原因有哪些？**
- 数据库慢 SQL、缺索引、锁竞争。
- 代码逻辑差、循环调用、大量计算。
- 缓存未命中或未使用缓存。
- 线程池/连接池不足，请求排队。
- 频繁 GC（内存不足）。
- 网络延迟、带宽瓶颈。
- 外部依赖接口慢。

**66. 什么是内存泄漏？性能测试中如何发现？**
内存泄漏指程序申请的内存无法被回收，导致可用内存持续减少。
发现方法：长时间稳定性测试中监控内存曲线，若内存持续增长不回落、频繁 Full GC 后仍不下降、最终 OOM，则可能存在泄漏。可用 jmap/MAT/heap dump 分析。

**67. 如何确定性能测试的并发数？**
- 根据生产环境监控/日志估算峰值 PV、在线用户数。
- 用公式换算（如 80%的访问集中在 20%的时间）。
- 参考业务预估（活动、大促目标）。
- 若无历史数据，采用递增加压找拐点。

**68. 性能测试环境为什么要接近生产环境？**
硬件配置、数据量、网络、中间件参数不同会导致测试结果失真。数据量太小可能测不出慢 SQL；配置差异会导致结论无法映射到生产，因此需尽量等比或同配。

## 六、安全测试

**69. 常见的 Web 安全漏洞有哪些？（OWASP Top 10 部分）**
SQL 注入、XSS 跨站脚本、CSRF 跨站请求伪造、越权访问、敏感信息泄露、文件上传漏洞、命令注入、SSRF、失效的身份认证、安全配置错误、不安全的反序列化。

**70. 什么是 SQL 注入？如何防范？**
攻击者在输入中拼接恶意 SQL 语句，改变原查询逻辑，达到窃取/篡改数据的目的（如 `' or 1=1 --`）。
防范：使用预编译/参数化查询(PreparedStatement)、ORM、输入校验与过滤、最小权限数据库账号、关闭详细报错。

**71. 什么是 XSS？有哪几种类型？如何防范？**
XSS(跨站脚本)：攻击者注入恶意脚本在受害者浏览器执行，窃取 Cookie/会话等。
类型：反射型（URL 参数）、存储型（存入数据库，危害最大）、DOM 型（前端 JS 操作）。
防范：输入过滤、输出编码/转义、设置 HttpOnly Cookie、CSP 内容安全策略。

**72. 什么是 CSRF？如何防范？**
CSRF(跨站请求伪造)：诱导已登录用户在不知情下发起恶意请求（借用其身份/Cookie）。
防范：CSRF Token、校验 Referer/Origin、SameSite Cookie 属性、敏感操作二次验证。

**73. XSS 和 CSRF 的区别？**
- XSS 是注入并执行恶意脚本，利用的是用户对网站的信任。
- CSRF 是伪造用户请求，利用的是网站对用户浏览器（Cookie）的信任。
- XSS 需要注入脚本，CSRF 不需要，只需诱导用户触发请求。

**74. 什么是越权漏洞？分几类？如何测试？**
越权指用户访问了本无权限访问的资源/功能。
- 水平越权：访问同级别其他用户的数据（改 userId 看别人订单）。
- 垂直越权：低权限用户访问高权限功能（普通用户调管理员接口）。
测试：修改请求中的资源 ID、越级调用高权限接口、抓包篡改参数，验证是否被拦截。

**75. 敏感信息泄露有哪些表现？如何测试？**
- 接口返回明文密码、身份证、手机号未脱敏。
- 报错信息暴露堆栈/SQL/服务器信息。
- 传输未加密(HTTP 明文)。
- URL 携带敏感参数。
- 备份文件、日志、配置文件可下载(.git、.svn、备份sql)。
测试：抓包检查响应、检查是否 HTTPS、构造异常看报错、扫描敏感路径。

**76. 密码相关的安全测试点有哪些？**
- 传输加密（HTTPS）。
- 存储加密（加盐哈希，不能明文/可逆）。
- 密码强度校验。
- 登录失败次数限制、账号锁定。
- 找回密码流程安全（防越权、验证码防爆破）。
- 密码不回显、不记录到日志。

**77. 什么是文件上传漏洞？如何防范？**
攻击者上传可执行脚本（如 webshell）获取服务器控制权。
防范：白名单校验文件类型（不只看后缀，校验文件头/MIME）、重命名文件、限制大小、上传目录禁止执行权限、隔离存储、内容安全扫描。

**78. 常用的安全测试工具？**
- 抓包/代理：Burp Suite（最常用）、Fiddler、Charles、mitmproxy。
- 漏洞扫描：AppScan、AWVS(Acunetix)、Nessus、OWASP ZAP、Xray。
- 注入：sqlmap。
- 端口扫描：Nmap。
- 综合：Metasploit、Nikto。

**79. 什么是暴力破解？如何防范？**
攻击者用大量账号/密码组合尝试登录。
防范：登录失败次数限制与锁定、图形/滑动/短信验证码、IP 限流、二次认证(2FA)、密码复杂度要求、异常登录告警。

**80. HTTP 和 HTTPS 的区别？HTTPS 如何保证安全？**
- HTTP 明文传输，HTTPS 在 HTTP 基础上加 SSL/TLS 加密。
- HTTPS 通过：非对称加密协商密钥 + 对称加密传输数据 + 数字证书验证服务端身份 + 数据完整性校验，防止窃听、篡改、冒充。

## 七、编程与算法

**81. 手写：反转字符串 / 判断回文。**
```python
def reverse(s):
    return s[::-1]

def is_palindrome(s):
    return s == s[::-1]
```

**82. 手写：统计字符串中每个字符出现次数。**
```python
from collections import Counter

def count_char(s):
    return dict(Counter(s))
```

**83. 手写：两数之和（LeetCode 1）。**
```python
def two_sum(nums, target):
    seen = {}
    for i, n in enumerate(nums):
        if target - n in seen:
            return [seen[target - n], i]
        seen[n] = i
```

**84. 手写：找出列表中出现次数最多的元素。**
```python
from collections import Counter

def most_common(nums):
    return Counter(nums).most_common(1)[0][0]
```

**85. 手写：列表去重且保持顺序。**
```python
def dedup(nums):
    seen = set()
    return [x for x in nums if not (x in seen or seen.add(x))]
```

**86. 手写：斐波那契数列。**
```python
def fib(n):
    a, b = 0, 1
    for _ in range(n):
        a, b = b, a + b
    return a
```

**87. 冒泡排序 / 快速排序原理？**
- 冒泡：相邻两两比较交换，每轮把最大值冒到末尾，时间复杂度 O(n²)。
- 快排：选基准值，分区（小于放左、大于放右），递归排序左右子数组，平均 O(nlogn)，最坏 O(n²)。

**88. 常见排序算法的时间复杂度？**
- 冒泡/选择/插入：平均 O(n²)。
- 快排/归并/堆排：平均 O(nlogn)。
- 归并、堆排最坏也是 O(nlogn)；快排最坏 O(n²)。

**89. Python 中列表和元组的区别？**
列表可变(mutable)、用 `[]`、可增删改；元组不可变(immutable)、用 `()`、可作字典 key、性能略高、更安全。

**90. Python 中深拷贝和浅拷贝的区别？**
- 浅拷贝(copy)：只复制外层对象，内部嵌套对象仍是引用。
- 深拷贝(deepcopy)：递归复制所有层级，完全独立。

**91. Python 中 == 和 is 的区别？**
- `==` 比较值是否相等。
- `is` 比较是否为同一对象（内存地址相同）。

**92. Python 中列表和字典的底层原理？查找复杂度？**
- 列表：动态数组，按索引访问 O(1)，查找元素 O(n)。
- 字典：哈希表，增删改查平均 O(1)。

## 八、数据库

**93. 内连接、左连接、右连接的区别？**
- 内连接(INNER)：只返回两表匹配的行。
- 左连接(LEFT)：返回左表全部 + 右表匹配，无匹配补 NULL。
- 右连接(RIGHT)：返回右表全部 + 左表匹配，无匹配补 NULL。

**94. 查询每个部门工资最高的员工（常考 SQL）。**
```sql
SELECT e.* FROM emp e
WHERE e.salary = (
  SELECT MAX(salary) FROM emp WHERE dept_id = e.dept_id
);
```

**95. 查询重复数据 / 删除重复数据。**
```sql
-- 查询重复的 name
SELECT name, COUNT(*) FROM student
GROUP BY name HAVING COUNT(*) > 1;
```

**96. 查询第二高的工资（经典题）。**
```sql
SELECT MAX(salary) FROM emp
WHERE salary < (SELECT MAX(salary) FROM emp);
```

**97. group by 和 having 的区别？having 和 where 的区别？**
- group by 按字段分组。
- where 在分组前过滤行，不能用聚合函数。
- having 在分组后过滤组，可以用聚合函数（如 `HAVING COUNT(*)>1`）。

**98. 索引的优缺点？什么时候不走索引？**
优点：加快查询速度。缺点：占用空间、降低增删改性能。
不走索引：like 以 `%` 开头、对字段用函数/运算、`!=`、`is null`、or 部分条件无索引、隐式类型转换、数据量太小。

**99. 索引有哪些类型？为什么用 B+ 树？**
类型：主键索引、唯一索引、普通索引、联合索引、全文索引。
B+ 树优势：矮胖结构减少磁盘 I/O、叶子节点链表便于范围查询、非叶子节点只存索引查询更快、数据全在叶子层查询稳定。

**100. 事务的 ACID 特性？**
原子性(Atomicity)、一致性(Consistency)、隔离性(Isolation)、持久性(Durability)。

**101. 事务的隔离级别？分别解决什么问题？**
- 读未提交(RU)：可能脏读。
- 读已提交(RC)：解决脏读，可能不可重复读。
- 可重复读(RR，MySQL 默认)：解决不可重复读，可能幻读。
- 串行化(Serializable)：全部解决，性能最差。

**102. drop、delete、truncate 的区别？**
- delete：DML，删数据可加 where，可回滚，删除慢。
- truncate：DDL，清空整表，不可回滚，速度快，重置自增。
- drop：DDL，删除整个表结构，不可回滚。

## 九、Linux / 网络 / 计算机基础

**103. 常用 Linux 命令？**
`grep`(查找)、`awk`/`sed`(文本处理)、`find`(查文件)、`tail -f`(实时看日志)、`ps -ef | grep`(查进程)、`netstat`/`lsof`(查端口)、`top`(看资源)、`chmod`/`chown`(权限)、`df`/`du`(磁盘)、`kill`(结束进程)。

**104. 如何在大文件中查找关键字并统计出现次数？**
```bash
grep "error" app.log            # 查找
grep -c "error" app.log         # 统计次数
grep -n "error" app.log         # 显示行号
grep -i "error" app.log         # 忽略大小写
tail -f app.log | grep "error"  # 实时监控
```

**105. 如何查看某端口被哪个进程占用？如何杀掉进程？**
```bash
lsof -i:8080          # 或 netstat -anp | grep 8080
kill -9 <PID>         # 强制杀掉进程
```

**106. 如何查看系统资源占用（CPU/内存/磁盘）？**
- CPU/内存：`top`、`htop`、`free -m`。
- 磁盘空间：`df -h`、`du -sh *`。
- I/O：`iostat`、`iotop`。

**107. TCP 三次握手、四次挥手？为什么握手三次、挥手四次？**
- 三次握手：SYN → SYN+ACK → ACK，建立连接，确保双方收发能力正常。
- 四次挥手：FIN → ACK → FIN → ACK，断开连接。
- 挥手四次：因为服务端收到 FIN 后可能还有数据要发，ACK 和 FIN 分开发送，所以比握手多一次。

**108. TCP 和 UDP 的区别？**
- TCP：面向连接、可靠、有序、有流量/拥塞控制，慢，用于文件传输、网页。
- UDP：无连接、不可靠、快、开销小，用于视频直播、游戏、DNS。

**109. 从浏览器输入 URL 到页面展示，发生了什么？**
DNS 解析 → 建立 TCP 连接(三次握手) → (HTTPS 则 TLS 握手) → 发送 HTTP 请求 → 服务器处理并返回响应 → 浏览器解析 HTML/CSS/JS 渲染页面 → 断开连接(四次挥手)。

**110. HTTP 常见状态码？**
200 成功、301/302 重定向、304 未修改、400 参数错误、401 未认证、403 无权限、404 未找到、500 服务器错误、502 网关错误、503 服务不可用、504 网关超时。

**111. 进程和线程的区别？**
- 进程：资源分配的最小单位，有独立内存空间，开销大。
- 线程：CPU 调度的最小单位，共享进程内存，开销小，通信方便，但一个线程崩溃可能影响整个进程。

## 十、场景 / 开放题

**112. 给你一个杯子，如何测试？**
- 功能：能否装水、是否漏水、容量是否准确、把手是否牢固。
- 界面：外观、颜色、材质、做工。
- 性能：装开水/冰水、承重、抗摔、耐高温。
- 安全：材质是否有毒、边缘是否割手、高温是否烫手。
- 兼容：装水/牛奶/酒/咖啡/碳酸饮料。
- 易用性：手感、重量、是否防滑、清洗是否方便。

**113. 如何测试电梯？**
- 功能：上下行、楼层按钮、开关门、报警按钮、超载提示。
- 性能：运行速度、最大载重、频繁使用。
- 安全：超载保护、断电应急、门夹人保护、急停。
- 界面：楼层显示、按钮灯、语音提示。
- 异常：多人同时按不同楼层、运行中按急停、断电、超载。

**114. 项目上线后出现线上 Bug 怎么处理？**
先评估影响面和严重程度 → 紧急止损（回滚/热修/降级）→ 保留现场（日志/数据）→ 定位根因 → 修复并验证 → 复盘（为什么漏测、如何补测试用例避免再犯）。

**115. 时间紧、任务重，如何保证测试质量？**
基于风险优先级排序，优先保证核心主流程和高风险模块；用探索性测试补充；复用自动化回归；与团队沟通明确取舍和风险，把未覆盖点作为风险上报；争取资源或延期。

**116. 如何提高测试覆盖率？**
需求评审阶段介入、用例评审、用覆盖率工具(JaCoCo/Coverage.py)度量、补充边界和异常场景、探索性测试、Bug 复盘分析漏测、建立测试用例库。

**117. 你和开发/产品有分歧时如何处理？**
基于事实和数据（需求文档、复现证据）沟通，对事不对人；理解对方立场；实在无法达成一致就升级到负责人/产品决策，并记录结论；以项目质量和用户体验为共同目标。

**118. 你觉得一个优秀的测试开发工程师应具备哪些能力？**
- 扎实的测试理论和用例设计能力。
- 较强的编码能力（Python/Java）。
- 自动化框架/平台开发能力。
- 熟悉数据库、Linux、网络、协议。
- 良好的分析定位和沟通能力。
- 质量意识、责任心、学习能力。

**119. 你平时如何学习和提升？**
关注技术社区/博客/公众号、看官方文档、动手做项目实践、阅读优秀开源框架源码、参与技术分享、复盘项目中的问题、刷算法题。

**120. 如何测试一个抢红包/秒杀功能？**
- 功能：抢到金额正确、总金额守恒、每人限领次数。
- 并发：高并发同时抢，验证不超发、不少发、无重复领取。
- 边界：红包被抢完的提示、剩余最后一个、金额为分的精度。
- 异常：网络中断重试是否重复领取、超时未领取的回退。
- 性能：大量用户瞬时并发下的响应和成功率。
- 安全：接口防刷、防重放、越权抢他人红包。
