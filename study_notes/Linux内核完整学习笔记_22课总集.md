## 1.2 贯穿全篇的核心哲学

**惰性 / 延迟（Laziness）**：不到万不得已不干活，把昂贵操作推迟到真正必要的那一刻；那一刻常常不会到来，成本就被省掉。
出现 3 次：COW（fork 时不拷、写时才拷）、虚拟内存超卖（用到才给物理内存）、多级页表（没用到的子树不建）。

**缓存（Cache）**：快设备与慢设备之间夹一层缓存，先打缓存、命中就不碰慢设备。
出现处：TLB（CPU↔页表）、Page Cache（内存↔磁盘）、dentry cache（路径↔inode）。

**隔离的视图制造独占幻觉**：用受限的视图让每个主体以为自己独占全部。
出现处：虚拟内存（每进程以为独占内存）→ namespace（每容器以为独占整套系统）。

**有事才通知 > 反复去问**（事件稀疏时）：
出现处：硬中断（vs 轮询）、epoll（vs select 轮询）、背压（满了才阻塞）。

**资源耗尽母题**：有限资源被大量"半死不活"的状态占住，新申请失败。
出现处：僵尸占 PID、inode 耗尽、TIME_WAIT 占端口、文件未关占 fd。

# 第二部分：五大子系统

## ① 进程管理

### 程序 vs 进程
- **程序**=静态文件（指令+数据，像菜谱）；**进程**=程序被加载进内存跑起来的动态实例（像照菜谱炒菜的过程）。
- 进程所有信息存在 `task_struct`。

### 并发假象与上下文切换
- 单核靠**时间片轮转**：CPU 毫秒级在进程间飞快切换，宏观同时、微观轮流。
- **并发**=宏观同时微观轮流（单核/asyncio）；**并行**=多核真同时（multiprocessing）。
- **上下文**=进程被暂停时必须保存、之后恢复的信息：① PC（执行到哪）② 寄存器（临时值）③ 内存映射/栈指针等。
- **上下文切换是纯开销**——这段时间 CPU 不做有用计算，纯"交接班"。

### 进程切换 vs 线程切换 ⭐
| | 进程切换 | 线程切换 |
|---|---|---|
| 寄存器/PC | 换 | 换 |
| 页表（地址空间）| **换** | 不换（共享）|
| TLB | **失效** | 不失效 |
| 开销 | 大 | 小 |

**完整因果**：两者都要存寄存器/PC（共同开销）。进程切换多了：① 切整套页表（MMU 指向新页表，x86 换 CR3）；② **TLB 失效**——TLB 缓存的是旧进程"虚拟→物理"翻译，因为隔离，同一虚拟地址在新进程映射到不同物理页，旧翻译一条不能用，整个作废 → 新进程刚跑时频繁未命中、走多级页表慢翻译。线程共享页表，不换、TLB 不失效，所以轻。

### 进程状态
**通用三态**：运行（在CPU上）/ 就绪（只缺CPU，排队）/ 阻塞（缺别的：IO、锁、信号）。
- 判断依据：**就绪只缺CPU，阻塞给了CPU也跑不了**。
- **不对称**：阻塞醒来必先回就绪排队，不能直接上CPU（因为唤醒时CPU不一定空）。

**Linux 五态（ps STAT列）**：
- R：运行/就绪
- S：可中断睡眠（可被信号叫醒，绝大多数睡眠）
- D：不可中断睡眠（等关键IO，**不响应信号，kill -9 都杀不掉**）
- T：停止
- Z：僵尸
- 💡 进程 kill -9 杀不掉 → 多半 D 状态，死等回不来的IO（NFS断、磁盘故障）。

### 僵尸 vs 孤儿 ⭐
| | 僵尸 Zombie | 孤儿 Orphan |
|---|---|---|
| 定义 | 子死了+父没回收 | 父死了+子还活着 |
| 状态 | 已退出，残骸留进程表 | 仍在运行 |
| 危害 | **占PID**，堆积耗尽PID致无法建新进程 | 无害 |
| 归宿 | 父调 wait()/waitpid() 回收 | 被 PID 1(systemd) 收养 |

- **为什么有僵尸**：子退出时产生"成绩单"（退出码），父需读取，故保留残骸等父 wait()。
- **孤儿为什么被收养**：孤儿将来死时原父已不在，无人 wait() 会变无人回收的僵尸；systemd 收养=承担将来回收责任，是**防僵尸的安全网**。
- **排查**：`ps aux | awk '$8 ~ /Z/'`（CMD 显 `<defunct>`）。**僵尸不可杀，要治它爹**——找父进程PPID，修复/重启/杀父，父死后僵尸变孤儿被回收。

### fork + 写时复制 COW ⭐
- `fork()` **一次调用两次返回**：父得子PID，子得0，出错-1。靠返回值区分父子。
- `fork+exec` 是创建新程序的主流：fork出子进程→子exec加载新程序，整个内存映像被替换。
- **COW**：fork 时父子共享同一批物理页且标记**只读**，故 fork 极快；任一方写某页→触发保护异常→内核只复制**被写的那一页**。
- **COW 一定更高效吗？不一定**：它赌"大部分页 fork 后不被写"。赌赢（fork+exec，旧页没碰）→零拷贝；赌输（fork 后狂写大量页）→每页触发异常，异常处理开销让它反比直接批量拷贝更慢，还有内存延迟爆发风险（Redis 持久化 fork 子进程需关注）。

### CFS 调度 ⭐
- **核心规则一句话：永远挑 vruntime（虚拟运行时间）最小的进程跑**。用红黑树排序，取最左 O(log n)。
- **一条规则三个目标自动涌现**：
  - 不饿死：**不跑就不涨，不涨早晚变最小，最小必被调度** → 没人被永久跳过。
  - 优待I/O型：它们睡得多、vruntime小，醒来自动被优先调度。
  - 公平：长期 vruntime 被拉到相近水平。
- **vruntime"虚拟"在哪**：=真实运行时间按优先级加权。高优先级涨得慢（更易保持最小、分到更多CPU），低优先级涨得快。用 **nice 值**（-20~+19）调节。
- **min_vruntime**（公平性地板，防作弊）：单调递增水位线。睡久的进程唤醒时 vruntime 被钳到水位线附近，只给一次性小优待，无法靠"装睡攒赤字"霸占CPU。
- **实时调度**凌驾CFS之上：SCHED_FIFO（跑到主动让出/阻塞）、SCHED_RR（同级轮转）。只要有实时进程就绪，永远优先于普通进程。

## ② 内存管理

### 虚拟内存：一个谎言 ⭐
- **反直觉**：两个进程打印相同变量地址却互不干扰 → 因为地址是**假的（虚拟地址）**，被翻译到不同物理位置。
- 进程活在"独占整片内存"的幻觉里（虚拟地址空间），虚拟地址经页表(MMU)翻译成物理地址。
- **三大好处**：
  1. **隔离安全**：A的虚拟地址只翻译到A自己的物理页，碰不到B，野指针只祸害自己。
  2. **简洁幻觉**：程序员只管用连续从0开始的虚拟空间。
  3. **超卖**：承诺虚拟空间但物理内存惰性分配、用到才给，可换swap。

### 页表与多级页表 ⭐
- **页**=虚拟内存固定块(4KB)；**页框**=物理内存同样大小的块。
- **页表每进程一份**（不是全系统共用）——因为隔离要求同一虚拟地址在不同进程映射到不同物理页，必须各有一张表。（这也是进程切换要换页表的原因；线程共享地址空间=共享同一张页表。）
- **平坦页表不可行**：64位虚拟页约2³⁶个，每条8字节→2³⁹字节=512GB，单进程放不下，每进程还要一份。
  - 算法：2³⁶×8 = 2³⁶×2³ = 2³⁹ 字节；2³⁹/2³⁰(1GB) = 2⁹ = 512GB。
- **多级页表（树状+惰性）**：顶级表→下级表→...→末级表存真实映射。没用到的虚拟区域整棵子树不创建。x86-64 通常4级。成本512GB→几MB。本质是**时间换空间**（多查几层换只存用到的）。

### TLB ⭐
- 4级页表翻译一个地址要4次访存，太慢。
- **TLB**=CPU内极小极快的缓存，缓存最近"虚拟页→物理页框"翻译。流程：先查TLB→命中则0次查表→未命中才走4级、结果存进TLB。
- 因访存有**局部性**，TLB命中率常99%+。
- 闭环进程切换开销：换页表→TLB全作废→新进程频繁未命中走慢翻译。

### 缺页中断 ⭐
- 访问的虚拟页页表项无效→"扑空"→触发缺页中断，交内核。**它是中性机制，不一定是错误**。
- 内核查权限分两个相反结局：
  - **合法**（有权访问，只是惰性没分配）→ 悄悄补内存，程序无感。细分：①首次访问惰性分配 ②从swap换回（要读磁盘，慢，疯狂swap=thrashing抖动）。
  - **非法**（野指针/空指针/越界）→ 发 **SIGSEGV**，进程被杀，终端打印 `Segmentation fault`。
- 💡 **段错误真相**：野指针→缺页中断→内核查权限非法→SIGSEGV。

### malloc 真相：VSZ vs RSS ⭐
- `malloc(1GB)` 成功时**物理内存一字节没给**，只划出标记合法的虚拟地址区间。真正写某页时才缺页中断分配4KB。
- **VSZ**=申请的虚拟空间总量；**RSS**=真正占用的物理内存（实际写过的页）。VSZ通常远大于RSS。
- 💡 监控被测服务内存盯 **RSS**（判断是否撑爆物理内存），盯错VSZ会误判。

### OOM Killer ⭐
- **OOM**=物理内存+swap耗尽（≠buffer overflow缓冲区溢出，两回事）。
- 超卖超过头→大家纷纷写入兑现→内存耗尽→新缺页无法兑现→**OOM Killer断臂求生**：按 `oom_score` 挑分最高的（占物理内存越多越高）杀掉释放内存。可用 `oom_score_adj` 保护/献祭，避开关键系统进程。
- 💡 **排查口诀：服务进程无声消失、无crash日志 → 查 `dmesg` / syslog，找 `Out of memory: Killed process`**。压测把内存压爆、被测进程被OOM杀，是性能/稳定性测试高频场景。

## ③ 文件系统

### VFS 与"一切皆文件" ⭐
- 硬盘/键盘/管道/socket 本质天差地别，却用同一套 `open/read/write/close` 操作。
- **VFS（虚拟文件系统）**=内核的"抽象基类/接口"：定义统一操作，各种具体实现（ext4/socket/管道...）各自override。**对上暴露统一系统调用，对下要求实现统一接口，多态分发**。
- "一切皆文件"真义：**只要实现了VFS接口，就能被当文件操作**，统一成 fd。
- 💡 **epoll 能同时监听 socket/管道/fd**，正因为它们在VFS眼里全是fd——网络的IO多路复用扎根在"一切皆文件"。

### 四大对象 ⭐
| 对象 | 管什么 |
|---|---|
| **inode** | 文件本体：元数据+数据块位置，**无文件名** |
| dentry | 名字→inode 映射，构建目录树，可缓存(dentry cache) |
| file | 一次"打开"的实例，持有**读写偏移量** |
| superblock | 整个文件系统总账（类型/大小/inode总数）|

- **inode 不存文件名**：为了让名字与本体解耦，一个文件本体可挂多个名字（硬链接）。
- **inode vs file 区别**：inode是文件本身(全系统一个)；file是某次打开(可多个，各有独立读写偏移)。所以两进程各open同文件，各自读写位置独立。
- 💡 文件被打开后即使被rm（名字没了、链接数到0），只要还有进程持有fd，数据就不释放——"删了正在写的日志、空间却没释放"的根因。

### 硬链接 vs 软链接 ⭐
| | 硬链接 | 软链接(symlink) |
|---|---|---|
| 本质 | 直接指向inode的另一个名字 | 独立小文件，内容是"目标路径字符串" |
| 共享inode | 是 | 否 |
| 原文件删了 | 不受影响(链接数>0,数据还在) | 失效(悬空链接) |
| 跨文件系统 | 不能 | 能 |
- **rm 删的是**：名字条目+inode链接数减1。链接数到0才真正释放文件本体。

### inode 耗尽 ⭐
- 文件系统格式化时预分配**固定数量inode**，每个文件/目录哪怕空的也占1个inode。
- 现象：`df -h` 看磁盘还有空间，但建文件报 `No space left on device`——因为 **inode 用光了**（`df -i` 看 IUse% 100%）。
- 💡 常见诱因：程序疯狂生成海量小文件。**排查：df -h 看数据块空间，df -i 看inode，两个都要看**。

### Page Cache 与 write≠落盘 ⭐
- 磁盘比内存慢约**十万倍**。内存与磁盘间夹一层缓存 **Page Cache**。
- `write()` 只写进 Page Cache 就**立刻返回成功**（快、批量合并小写、读也命中）。未落盘的修改叫**脏页**，内核异步**回写**。
- 💡 第二次cat同一大文件更快=Page Cache命中。

### fsync 与可靠性 ⭐
- **`write()` 成功只保证"交给内核Page Cache"，不保证落盘**。此刻断电→脏页随内存丢失。
- **`fsync(fd)`** 阻塞直到脏页真正回写到磁盘才返回。可靠写=write()+fsync()。
- **权衡**：不fsync快但有丢数据窗口；每笔fsync可靠但慢（要等磁盘）。**没有免费的可靠性**。
- 数据库用 **WAL（预写日志）+ 顺序fsync**：改动先顺序追加写日志、只fsync日志（顺序写快、只fsync一个文件），数据文件稍后异步刷。断电后重放WAL恢复。
- 💡 **测开实战**：测"写成功就不丢"的承诺，用**故障注入**——系统报成功（精确卡在ack返回那一刻）后立即模拟断电/kill-9，重启查数据是否还在、是否一致。区分kill-9（只丢内存）和断电（连未刷盘脏页都丢）。

## ④ 进程间通信 IPC

> 隔离是默认的墙，IPC 是墙上受控的门。不同的门传不同的东西。

### 管道 pipe
- 内核内存里的缓冲区，写端→读端。**单向、字节流无边界、读完就没、仅亲缘进程**。
- 亲缘限制原因：靠 **fork 时子进程继承父进程的fd** 来共享，无亲缘=拿不到同一对fd。
- 💡 字节流无边界 = TCP粘包同源。
- **背压**：缓冲区满，写方再write会**阻塞**(进S状态)，等读方取走才唤醒；空了读方阻塞。**满了写阻塞、空了读阻塞，自动做生产者-消费者速度匹配**——这就是背压，分布式/并发稳定性核心（Kafka堆积、TCP流控、线程池拒绝策略同理）。

### 命名管道 FIFO
- 文件系统里有真实路径名(`mkfifo`)，陌生进程靠**路径名相认**即可用，不需亲缘。数据特性同管道。

### 信号 signal
- 只传"通知"无数据，异步。SIGINT(Ctrl+C)、SIGKILL(kill -9)、SIGTERM(可捕获,优雅关闭)、SIGSEGV(段错误)、SIGCHLD(子退出提醒父回收)。
- **SIGKILL/SIGSTOP 不可捕获、不可忽略**——所以kill -9霸道。SIGTERM可捕获→优雅关闭用它（停止收新请求、处理完手头、释放资源再退）。

### 共享内存 + 信号量 ⭐
- **共享内存**=内核把同一块物理内存映射进两进程地址空间，**零拷贝、不进内核、最快**。实现=两进程页表项指向同一物理页框（故意打破隔离）。
- 但只给"共享"不给"同步"→会有 **race condition**，必须配**信号量**做互斥。
- **信号量**=不传数据的"信号灯/计数器"，给共享资源上锁。二元信号量(0/1=互斥锁)、计数信号量(N=限量,如连接池)。
- ⚠️ 信号量只是约定，不强制——靠所有参与方自觉"先拿锁再访问"。

### 消息队列
- **有消息边界**（vs 管道无边界），可按类型/优先级选择性读。适合进程间异步任务投递。
- 记忆：管道=水流(无边界)，消息队列=信箱(一封封,可挑选)。

### socket ⭐
- **唯一能跨机器**的IPC。也能本机用（**Unix Domain Socket, UDS**）。
- 本机通信：UDS 比 `127.0.0.1` TCP **更快**（不走完整TCP/IP栈，不算校验和、不封IP头）**且更安全**（文件路径+权限控制、不占端口、不暴露网络）。
- 💡 MySQL(`mysql.sock`)、Docker(`docker.sock`)本机连接默认UDS。MySQL 中 `localhost` 常走UDS、`127.0.0.1` 强制走TCP——本机连不上时分清走哪条。

**IPC 选型一句话**：跨机器→只能socket；本机要快/传大数据→共享内存+信号量；本机简单流式→管道；只需通知→信号；要消息边界/异步解耦→消息队列。

## ⑤ 网络协议栈

### 收包路径（网卡→应用）
```
①网卡收到比特流 →DMA直接写入内存→ ②内核接收ring buffer
→ 网卡发【硬中断】 → ③CPU响应硬中断(只做最少事) → 触发【软中断】
→ ④软中断里协议栈逐层解析(IP查路由/校验 → TCP查端口找socket/排序/去重/ACK)
→ ⑤数据放入该socket的接收缓冲区 → ⑥唤醒阻塞在该socket的进程
→ ⑦用户recv()：数据从内核socket缓冲区【拷贝】到用户空间
```

### 硬中断/软中断（上半部/下半部）⭐
- **餐馆比喻**：服务员=CPU，门铃=网络包到达的硬中断。若门铃一响就把客人从头伺候到尾(20分钟)，期间新门铃没空理→餐馆瘫痪。聪明做法：门铃响只说句"请稍等"(2秒)马上回岗→稍后再慢慢点菜上菜。
- **为什么分两半**：硬中断会打断CPU一切、且执行时屏蔽其他中断。若把协议栈解析全塞硬中断里，高流量下CPU被海量硬中断淹没、无暇调度进程→卡死（中断风暴/receive livelock）。
- **硬中断(上半部)**：只做最紧急最少的事(确认收包)，立刻返回，让CPU能继续响应新中断/调度。
- **软中断(下半部)**：耗时的协议栈解析推迟到这里、在**开着中断**的环境从容做。
- 一句话：硬中断快进快出只应答"包收到了"，耗时拆包扔给软中断慢慢做，CPU 不被拖死。

### NAPI（中断↔轮询自适应）
- 低流量用中断(响应及时)；高流量网卡**关中断改轮询**(内核主动批量捞包)，省掉海量中断开销。
- 中断适合事件稀疏(省CPU)，轮询适合事件密集(省中断开销)，NAPI自适应切换。

### epoll ⭐
- **C10K问题**：一连接一线程→海量上下文切换+栈内存，扛不住；一线程挨个轮询→99%连接没数据，全是空转。
- **I/O多路复用核心**：把海量fd交给内核，线程睡觉等；内核帮你盯，哪个就绪就挑出来叫醒你，只处理就绪的那几个。**"内核帮你盯、有事才通知" vs "自己反复问"**。
- **epoll vs select/poll**：
  | | select/poll | epoll |
  |---|---|---|
  | 名单交接 | 每次整份拷贝全部fd | 一次注册常驻内核(红黑树) |
  | 内核找就绪 | 遍历检查所有 | 回调:就绪fd自己进就绪列表 |
  | 返回 | 返回全部,用户再遍历找 | 只返回就绪的那几个 |
  | 开销随连接数 | **线性增长** | **几乎恒定(只和活跃数有关)** |
- **实现**：红黑树管"全集"(增删查fd O(log n))，就绪列表(双向链表)管"就绪子集"。数据到达socket时内核回调把fd塞进就绪列表，无需遍历。
- 一句话：**select开销取决于"盯多少连接"，epoll取决于"多少连接真来数据"**。
- **LT vs ET**：
  - LT(水平触发,默认)：只要还有没读完的数据就一直通知。安全、简单。
  - ET(边缘触发)：只在数据从无到有那一刻通知一次，**必须一次读干净**否则剩余数据卡住收不到。性能略高但难写。
  - 💡 服务某些连接偶尔卡住收不到数据→怀疑ET模式没把数据一次读干净(Nginx/Redis多用ET)。

### 零拷贝 sendfile ⭐
- **传统"读文件发网络"**：磁盘→(DMA)→内核PageCache→(CPU拷贝)→用户buf→(CPU拷贝)→内核socket缓冲→(DMA)→网卡。**4次拷贝+2次态切换**。
- **荒唐处**：数据从内核PageCache拷到用户buf、用户程序啥也没改、又拷回内核socket缓冲——出差用户空间转一圈纯属多余。
- **sendfile（基础版）**：数据全程留内核，态切换2→1、CPU拷贝2→1（砍掉去用户空间那趟）。
- **带DMA收集的sendfile（完全体）**：网卡DMA直接从PageCache读走，连最后一次CPU拷贝也省→**真正零CPU拷贝**(DMA还在搬,但CPU不用亲自搬)。
- **价值**：CPU从"搬数据"苦力里解放，同样CPU服务多得多的连接，吞吐上台阶。
- 💡 Kafka(消息从磁盘PageCache直接怼网卡)、Nginx(`sendfile on`)、CDN离不开它。压测发现CPU大量耗在内存拷贝→怀疑没用零拷贝。

# 第三部分：横切主题

## 并发与同步

### i++ 不原子 → 竞态条件 ⭐
- `i++` 在CPU眼里是**三步：读(内存→寄存器)、改(+1)、写(回内存)**，中间可被切换打断。
- 两线程同时i++(初值5)，倒霉时序：A读5、B也读5(A还没写回)、A写6、B写6→结果6而非7，**丢了一次更新**。
- **竞态条件**：多线程同时读写同一数据，结果取决于不可控的执行时序→bug时有时无、极难复现。
- `i++` 不是**原子操作**(不可被打断的"要么全做要么没做")，故多线程不安全。
- 💡 **GIL**：用一把大锁保证同一时刻只有一个Python线程执行字节码，从根上回避竞态。代价=无法真正并行用多核(CPU密集型要用multiprocessing)。GIL≠OS调度——OS调度是"谁来跑"，GIL是"保证同一时刻只一个Python线程跑"。

### 锁、临界区、互斥
- **临界区**=会读写共享数据、必须保护的代码段。
- **互斥**=保证同一时刻最多一个线程进临界区。`lock()`→临界区→`unlock()`。

### 自旋锁 vs 互斥锁 ⭐
- 拿不到锁怎么等？两种等法：
| | 自旋锁 spinlock | 互斥锁 mutex |
|---|---|---|
| 拿不到锁时 | 原地空转反复查(忙等) | 睡眠,让出CPU,等被唤醒 |
| 开销 | 空转浪费CPU,但无切换开销 | 有睡眠/唤醒的上下文切换开销 |
| 适合 | 临界区极短(<一次切换) | 临界区长/可能阻塞睡眠 |
| 持锁时能否睡眠 | 绝对不能 | 可以 |
| 典型 | 内核中断处理、多核短临界区 | 应用层、要做IO的临界区 |
- **核心权衡**：自旋锁赌"很快能拿到,空转比睡划算";互斥锁认"要等挺久,睡比空转划算"。分界=持锁时间 vs 一次切换开销。
- ⚠️ 自旋锁绝不能在持锁时睡眠(否则别人永远空转烧死CPU)；单核上自旋锁几乎无意义(B自旋占着唯一CPU,A没机会释放)。

### 死锁 ⭐
- A攥锁1等锁2，B攥锁2等锁1，互相等对方手里的、永不放手→**卡死**(区别于竞态的"算错")。
- **四个必要条件(缺一不可,破坏任一即可防)**：
  1. **互斥**：资源独占
  2. **持有并等待**：攥着已有的还去等新的、等待时不释放
  3. **不可剥夺**：不能硬抢
  4. **循环等待**：等待形成环
- **最常用破解=破坏循环等待**：**锁排序**(所有线程按全局统一顺序拿锁)。因为没抢到锁1的线程手里啥都没有，不可能攥着锁2去和别人成环——所有等待箭头同向，永不闭合成环。
- 💡 **测开排查口诀：服务卡死 + CPU很低(线程都在睡着等锁) → 怀疑死锁 → 抓线程栈(jstack)看谁等谁**。死锁难复现(依赖时序)，靠提高并发度压测暴露。

### 读写锁 + RCU ⭐
- 互斥锁在读多写少时亏：读读本不冲突(竞态根源是写)，却被逼串行。
- **读写锁**：读锁(共享,多读并行)、写锁(独占)。规则：读读共享、读写互斥、写写互斥。洞察=**只有写才需独占**。
- 但读锁本身在多核下仍有开销(争抢读者计数器)。
- **RCU(Read-Copy-Update)**：让**读端零开销、无锁**。写者不动原数据，而是 **Copy**(复制副本)→在副本上**Update**→**原子切换指针**→等**宽限期**(所有老读者读完)再回收老数据。读者顺指针读，要么完整老版本要么完整新版本，绝不读到改一半→无需加锁。
  - 读者能不加锁，**因为写者从不在读者正在读的那份数据上动手**。
  - 取舍：读端极快，写端复杂慢，**只适合读极多写极少**(内核路由表/配置)。
- 进化逻辑：互斥锁(读也排队)→读写锁(读读放行)→RCU(读端零开销,代价全甩给写端)。

## 性能排查工具链

### 总纲：四资源 × USE ⭐
- 不背命令，先建地图：性能问题=某**资源**瓶颈。四资源=**CPU、内存、磁盘IO、网络**。
- **USE方法**：对每个资源问 **U**tilization(使用率,多忙)/ **S**aturation(饱和度,有没有排队)/ **E**rrors(错误)。
- **精髓在 Saturation**：使用率高未必是问题(可能物尽其用)，**"开始排队等待"才是变慢的真信号**。
- **先分诊(哪个资源)，后深挖(对应工具)**。

### CPU：top 分诊 ⭐
- **load average**(1/5/15分钟)：=运行+等待CPU/IO的任务数，对应饱和度。**判断高低要除以CPU核数**(负载8/8核=1健康，8/2核=4过载)。看三数趋势判断恶化/缓解。
- **CPU分量**：
  - us(用户态)高→应用在狂算(死循环/低效算法)
  - sy(内核态)高→大量系统调用/上下文切换/锁竞争
  - wa(iowait)高→**CPU在干等磁盘IO，瓶颈在磁盘不在CPU**(回扣D状态)
  - id(空闲)高但仍慢→CPU非瓶颈，可能卡锁(死锁)/网络/外部依赖
- 💡 经典误判：CPU使用率不高就说"CPU没问题"，但wa高说明在等磁盘→该转iostat。

### strace：看系统调用 ⭐
- 把程序运行时发的每个系统调用实时打印。**因为系统调用是用户程序碰外部世界的唯一通道，录下它=看穿程序真实行为**(看到的是真在做的，不是日志声称的)。
- 读法：看"调了什么+返回什么"，**返回负数带错误码的那行往往是根因**：ENOENT(文件不存在)、EACCES(权限不够)、ECONNREFUSED(连接被拒)、ETIMEDOUT(超时)。
- 两大实战：① 卡死时看"停在哪个系统调用"(停在futex=等锁/可能死锁，停在read=等数据，停在connect=等连接)；② `strace -c` 统计哪类调用最频繁/最耗时(接sy高的深挖)。
- ⚠️ strace会让程序显著变慢，生产关键服务慎用。
- 卡在read(fd)→先查fd是什么(`ls -l /proc/PID/fd/N` 或 lsof)，才能定位等谁，别直接猜网络。

### 内存：free/available/泄漏 ⭐
- **看内存够不够看 `available`，不看 `free`**！因为Linux信奉"空闲内存即浪费"，主动把空闲内存拿去做Page Cache，所以free天然很小；但缓存随时能让出还给程序，**available=free+可回收缓存**才是真正可用量。
- 内存真出问题=available逼近0 + `vmstat`的 **si/so**(swap in/out)持续非0(在疯狂换页=饱和=thrashing)。
- **内存泄漏识别靠RSS趋势**(不是某一刻占多少)：负载稳定却RSS持续单调上涨、用完不回落、永不回基线→泄漏。
- 💡 **测开：长稳/浸泡测试(soak test)**——稳定负载持续压几小时~几天，记录RSS曲线，只涨不回落判定泄漏。串起OOM+RSS。

### 磁盘IO：iostat ⭐
- **别只看 %util**！`%util`=磁盘有IO处理的时间占比(忙不忙)。**SSD/磁盘阵列能并行处理多个IO，%util=100%不代表处理能力到顶**，故SSD上%util=100%不能直接判瓶颈(它是使用率Utilization)。
- **看 `await`**(单个IO平均耗时:排队+处理)：才是磁盘卡不卡的真信号(对应饱和度)。SSD正常零点几~几毫秒，HDD几~十几毫秒，飙高=在排队=瓶颈。
- 一句话：%util看"忙不忙"(可能假象)，await看"卡不卡"(真信号)，判瓶颈以await为准。
- 完整链：top看wa高→iostat看await飙高→iotop找狂读写的进程→strace看它做什么IO。

### 网络：ss / TIME_WAIT ⭐
- 看连接用 `ss`(netstat现代替代)。重点两个堆积状态：
- **TIME_WAIT**：主动关闭方发完末ACK后进入，等2MSL。
  - **为什么存在(不是bug)**：① 确保末ACK对方收到(丢了对方重发FIN时能补发ACK) ② 让旧连接残留包自然消亡，避免干扰新连接。
  - **为什么服务器堆积**：短连接场景服务器是主动关闭方，每处理一请求产生一个TIME_WAIT，高并发瞬间堆几万。
  - **为什么致新连接建不了**：每个TIME_WAIT占一个本地端口约几十秒，本地端口总共约6万多个，堆几万→端口耗尽→新连接无端口可用而失败(回扣"资源耗尽"母题)。
  - 缓解：客户端主动关/长连接连接池复用/调tcp_tw_reuse(注意tcp_tw_recycle在NAT下有坑、已移除)。
- **CLOSE_WAIT**：被动关闭方收到FIN后进入，**等自己的应用调close()推进**。
  - **大量堆积≈应用bug**：从CLOSE_WAIT往下必须应用主动close()，应用忘了close()(异常路径没关/连接泄漏)→永远卡在CLOSE_WAIT、不会自愈、越积越多。
- **本质区别一句话：TIME_WAIT堆积怪架构(短连接太多,正常机制副作用)，CLOSE_WAIT堆积怪代码(忘了close,实打实bug)**。排查第一步分清哪个状态堆积，直接决定调架构还是抓bug。

## 用户态/内核态 + 系统调用

### 为什么分两态 ⭐
- 程序不可信(可能有bug/恶意)。若都能直接操作硬件、读写任意物理内存→① 稳定性崩塌(一个程序bug改写别的程序甚至内核内存、拖垮系统) ② 安全性崩塌(恶意程序读走别人数据/格盘) ③ 无隔离。
- CPU硬件设两个特权级：**内核态**(至高权限,能执行所有指令、访问所有物理内存、操作硬件,内核运行于此)、**用户态**(受限,碰不了硬件和任意内存,应用运行于此)。
- 核心思想：**把危险能力收归内核独享，普通程序关进用户态沙箱，危险操作必须求内核、经内核检查**。
- 回扣：段错误(用户态无权碰内存→内核拦截)、虚拟内存隔离、strace(守在用户态→内核态关卡上看一切)。

### 系统调用：唯一受控的门 ⭐
- 用户态进内核态不能随便跳，只能执行特殊指令(x86-64的`syscall`/老式`int 0x80`)触发**陷入(trap)**：CPU切到内核态、跳到内核**预先规定的固定入口**。
- **受控在哪**：不能跳内核任意位置，只能从固定入口进、报上**系统调用号**、查系统调用表找对应函数执行。"只有一道门、进门按号办事"，无法翻墙乱跑→隔离不被绕过。
- 流程：用户态→syscall(陷入)→切内核态跳固定入口→查调用号执行内核函数→返回结果→切回用户态→继续。
- **为什么"贵"**：那个"切到内核态再切回"有实实在在开销(保存/恢复用户态现场、切栈)。比进程切换轻(不换页表/TLB)但非免费。**高频系统调用(如一次读1字节循环百万次=百万次切换)累加开销可观**→正是sy高的典型原因，`strace -c`能抓。
- **优化=减少系统调用次数**：用**缓冲**(一次读4KB到用户缓冲区慢慢取,而非一次1字节)、**批量化**(sendfile一次干完读+发、io_uring)。

## 容器底层（namespace + cgroup）

### 容器 ≠ 轻量虚拟机 ⭐
- **VM**：模拟整套虚拟硬件+装完整独立操作系统内核。一机跑3VM=3个完整内核+宿主机内核。重。
- **容器**：**没有自己的内核，所有容器和宿主机共用同一个Linux内核**。容器本质=宿主机上一个(组)被"圈养"的普通进程。
- **一句话定义**：容器 = 普通进程 + namespace(隔离) + cgroup(限额) + 联合文件系统(打包)。无虚拟硬件、无独立内核。
- **为什么比VM轻快**：启动容器=启动进程(毫秒级)；启动VM=启动整个操作系统(几十秒)。**因为容器省掉了"独立内核+虚拟硬件"这整套重东西**，只给进程加隔离和限额。

### namespace（隔离）
- 内核的"隔离视图"机制：**让进程看到的某类资源是限定的独立一份,而非全局全部**。
- 类型：PID(进程)、Network(网络)、Mount(挂载)、UTS(主机名)、User(用户)、IPC。
- 回扣：是**虚拟内存隔离思想的推广**——虚拟内存让进程以为独占内存，namespace让容器以为独占整套系统资源。
- 💡 容器内主进程PID=1，但宿主机看它是个大号PID(如8537)——同一进程在容器PID namespace里是1、全局是8537。

### cgroup（限额）
- namespace只解决"看不见别人"，但所有容器**共用宿主机同一份物理CPU/内存**，一个容器狂吃会拖垮别人。隔离了视图、没隔离用量。
- **cgroup**=给一组进程设资源上限(CPU/内存/IO带宽)，超过就限制或处置。
- 回扣：cgroup内存限制→超限触发**OOM**杀容器内进程(容器"莫名被OOM killed"，dmesg可见)；CPU限制→关联调度。cgroup不是新东西，是把OOM/调度按"组"施加配额。
- **分工一句话**：**namespace管"你能看到什么"(隔离视图)，cgroup管"你能用多少"(资源配额)**，缺一不可。

# 第四部分：高频面试题（总-分-例）

### Q1 进程vs线程？为什么进程切换更贵？
**总**：进程是资源分配单位、线程是CPU调度单位；进程切换贵在切页表+TLB失效。
**分**：进程有独立地址空间，线程共享所属进程地址空间(只独享寄存器/栈/PC)；两者切换都存寄存器(共同开销)；进程切换额外要切整套页表(MMU指新页表)+TLB失效(旧进程虚拟→物理翻译全作废,因隔离同一虚拟地址映射不同物理页)→新进程频繁未命中走慢翻译；线程共享页表故不换、TLB不失效。
**例**：Python multiprocessing重、threading轻，对应进程重线程轻。

### Q2 僵尸vs孤儿？怎么处理僵尸堆积？
**总**：僵尸=子死父没回收(占PID)，孤儿=父死子活(被systemd收养无害)。
**分**：僵尸保留退出状态等父wait()，父不回收会堆积耗尽PID；孤儿被PID1收养以防其将来死后变无人回收的僵尸；处理僵尸要找父进程修复/重启/杀父(治爹不杀尸)。
**例**：`ps aux|awk '$8~/Z/'` 找defunct。

### Q3 进程kill -9杀不掉？
**总**：多半D状态(不可中断睡眠)，死等回不来的IO。
**分**：D状态等关键IO不能被打断、不响应任何信号(含SIGKILL)；常因NFS断/磁盘故障；只能恢复IO或重启。
**例**：ps看STAT=D且关联已断NFS。

### Q4 fork和COW？COW一定更高效吗？
**总**：fork复制进程(一次调用两次返回)，COW写时才按页复制；fork+exec近零成本，但fork后大量写反而更慢。
**分**：COW赌"大部分页fork后不被写"。fork+exec旧页没碰=零拷贝(赌赢)；fork后狂写每页触发缺页异常,异常开销使总成本反超直接批量拷贝(赌输),还有内存延迟爆发。
**例**：Redis RDB持久化fork子进程依赖COW,主进程大量写时内存可能骤增触发OOM。

### Q5 CFS怎么既公平又不饿死？
**总**：仅靠"总挑vruntime最小的跑"一条规则自动实现。
**分**：vruntime=真实时间按优先级加权(高优先级涨得慢);红黑树取最左;不跑就不涨、长期不跑早晚变最小必被选中(不饿死);睡得多的I/O进程vruntime小被优先(优待I/O);min_vruntime兜底防装睡霸占。
**例**：编辑器(I/O)与编译(CPU)并存,敲键盘立即响应、编译空隙推进,都不饿死。

### Q6 malloc(1GB)成功=拿到1GB物理内存了吗？VSZ vs RSS？
**总**：不会,只给虚拟地址空间,物理内存写时才按页分配。
**分**：malloc成功只是划出标记合法的虚拟区间并返回起始地址;真正写某页才缺页中断分配4KB;VSZ=申请的虚拟量,RSS=真占用的物理内存,VSZ常远大于RSS。
**例**：监控被测服务盯RSS判断是否撑爆物理内存。

### Q7 磁盘有空间却报No space left？
**总**：inode耗尽。
**分**：格式化时预分配固定数量inode,每个文件哪怕空的也占1个;海量小文件会先耗光inode而数据块还有空间;df -h看数据块、df -i看inode,两个都要看。
**例**：日志框架疯狂生成小文件,df -i IUse%=100%。

### Q8 write成功后断电会丢吗？怎么确保不丢？
**总**：会丢,write只保证进Page Cache不保证落盘,要fsync。
**分**：write成功=数据交给内核Page Cache(脏页),此刻断电脏页随内存丢失;fsync阻塞至脏页真正落盘才返回;可靠性vs性能权衡;数据库用WAL+顺序fsync既快又不丢。
**例**：测"写成功不丢"用故障注入——ack返回瞬间断电/kill-9,重启查数据,区分kill-9(丢内存)和断电(丢未刷盘脏页)。

### Q9 几种IPC怎么选？最快是哪个？
**总**：跨机器只能socket;本机要快传大数据用共享内存(+信号量);最快是共享内存。
**分**：共享内存零拷贝不进内核(两进程映射同一物理内存)故最快,但需信号量同步防race;管道无边界字节流仅亲缘;消息队列有边界可挑选;信号只传通知;socket唯一跨机器,本机UDS比本地TCP快且安全。
**例**：本机大数据传输用共享内存+信号量;MySQL本机连接走UDS。

### Q10 epoll为什么比select高效？
**总**：select每次整份拷贝+遍历全部,开销随连接数线性增长;epoll红黑树常驻+回调进就绪列表,开销只和活跃数有关。
**分**：select每次调用把全部fd拷给内核、内核遍历检查、返回后用户再遍历找就绪;epoll一次注册fd常驻内核红黑树、数据到达时回调把就绪fd塞进就绪列表、只返回就绪的几个。
**例**：一万连接只10个活跃,epoll只为这10个干活。

### Q11 i++为什么不是线程安全的？
**总**：i++不原子(读改写三步可被打断),多线程交错丢更新。
**分**：i++=读(内存→寄存器)/改(+1)/写(回内存)三步;两线程都在A写回前读到旧值→基于旧值各加1→互相覆盖→丢一次更新;这就是竞态条件,结果取决于不可控时序、bug时有时无难复现。
**例**：GIL用大锁保证同一时刻只一个Python线程执行字节码来回避竞态,代价是无法并行用多核。

### Q12 自旋锁和互斥锁怎么选？
**总**：临界区极短用自旋锁,临界区长/可能阻塞用互斥锁。
**分**：自旋锁原地空转死等(浪费CPU但无切换开销),互斥锁睡眠等唤醒(有切换开销);锁占几纳秒时空转比睡(切换开销)划算→自旋锁,锁占很久(等IO)时睡比空转几毫秒划算→互斥锁;权衡=持锁时间vs一次切换开销。
**例**：内核中断处理(不能睡)用自旋锁,应用层要做IO的临界区用互斥锁。

### Q13 死锁四条件？怎么破？
**总**：互斥+持有并等待+不可剥夺+循环等待(缺一不可),最常用破坏循环等待(锁排序)。
**分**：四条件同时满足才死锁,破坏任一即可;锁排序=所有线程按全局统一顺序拿锁,没抢到锁1的线程手里啥都没有、不可能攥锁2成环,等待箭头同向永不闭合。
**例**：测开排查——服务卡死+CPU很低→怀疑死锁→抓线程栈看谁等谁。

### Q14 系统慢了怎么系统地排查？
**总**：先分诊"哪个资源"再深挖,四资源(CPU/内存/磁盘/网络)×USE(使用率/饱和度/错误),重点看饱和度(有没有排队)。
**分**：top看load average(除核数)和CPU分量(us应用/sy内核/wa等磁盘/id空闲)做第一层分诊;wa高转iostat看await;sy高用strace -c;内存看available和si/so。
**例**：id高+wa=40%→瓶颈在磁盘不在CPU→iostat看await实锤。

### Q15 容器和VM本质区别？namespace vs cgroup？
**总**：容器共用宿主机内核、本质是普通进程,VM有独立内核+虚拟硬件;namespace管隔离、cgroup管限额。
**分**：容器省掉独立内核+虚拟硬件故毫秒启动(VM几十秒);namespace让容器只看到自己的进程/网络/文件(隔离视图),但容器共用宿主机物理CPU/内存,故需cgroup限制每个容器最多用多少资源防止吃光饿死邻居。
**例**：容器内存超cgroup上限触发OOM被杀,dmesg可见。
