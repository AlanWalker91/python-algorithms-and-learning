**贯穿全篇的一个核心哲学——「惰性 / 延迟 (Laziness)」**：
不到万不得已不干活，把昂贵操作推迟到真正必要的那一刻；很多时候那一刻根本不会到来，成本就被彻底省掉。
本笔记中它出现了三次：
1. **COW**（fork 时不拷贝，写时才拷）
2. **虚拟内存超卖**（承诺虚拟空间，物理内存用到才给）
3. **多级页表**（没用到的地址区域，整棵子树不创建）

# 第一部分：进程管理

## 1. 基础概念：程序 vs 进程

| 维度 | 程序 (Program) | 进程 (Process) |
|------|---------------|----------------|
| 状态 | 静态 | 动态 |
| 本质 | 硬盘上的文件（指令+数据集合） | 程序被加载进内存、真正跑起来的「活实例」 |
| 类比 | 菜谱（写在纸上） | 照着菜谱真正炒菜的整个过程 |

- 一个程序可对应多个进程（开两个 Chrome 窗口 ≈ 两个进程，共用一份「菜谱」各炒各的）。
- 进程的所有信息记录在进程描述符 **`task_struct`** 中（PID、状态、优先级、内存映射、打开的文件等）。

## 2. 并发的假象与上下文切换

**核心问题**：单核 CPU 一次只能执行一条指令，为什么感觉多个进程同时运行？

**答案**：**时间片轮转 + 进程切换**。CPU 把时间切成毫秒级小片，飞快地在进程间轮流切换，宏观「同时」、微观「轮流」。

- **并发 (Concurrency)**：宏观同时、微观轮流（单核轮转、`asyncio` 单线程）。
- **并行 (Parallelism)**：多核真正同时执行（`multiprocessing` 多核）。

**上下文 (Context)**：进程被中途暂停时，必须保存、之后要恢复的全部信息：
1. **程序计数器 (PC)** —— 下一条要执行的指令地址（"我炒到哪一步了"）
2. **寄存器 (Registers)** —— 临时计算结果、中间变量（"手头正拿着什么"）
3. **内存映射、栈指针、打开的文件等**（"整体上下文"，打包在 `task_struct` 里）

**上下文切换 (Context Switch)**：保存当前进程上下文 + 加载下一进程上下文的整个动作。
> ⚠️ 它是**纯开销**——这段时间 CPU 没做任何有用计算，纯属"交接班"损耗。切换越频繁，浪费越多。

### 进程切换 vs 线程切换（高频考点）

| | 进程切换 | 线程切换（同进程内） |
|---|---|---|
| 寄存器 / PC | 要换 | 要换 |
| **页表（地址空间）** | **要换** | **不换**（共享） |
| **TLB** | **失效** | 不失效 |
| 开销 | **大** | 小 |

**为什么进程切换更贵**（完整答案）：
> 线程共享地址空间（同一张页表），切换时不需要切换页表；进程切换要换整套页表（MMU 指向新页表树根，x86 上换 CR3），还会导致 **TLB 失效**——旧进程缓存的"虚拟页→物理页框"翻译全部作废（因为隔离，同一虚拟地址在新进程映射到不同物理页），新进程刚跑时每次访存都未命中、要走多级页表慢翻译，直到 TLB 被重新焐热。这部分页表/TLB 代价是线程切换没有的。

## 3. 进程的状态

### 通用三态模型

| 状态 | 含义 | 判断依据 |
|------|------|---------|
| **运行态 (Running)** | 正在 CPU 上执行 | — |
| **就绪态 (Ready)** | 万事俱备只欠 CPU，在就绪队列排队 | **只缺 CPU**，给了就能跑 |
| **阻塞态 (Blocked)** | 在等某事件（I/O、锁、信号） | **给了 CPU 也跑不了**，缺的是别的东西 |

**状态转换图**（注意"不对称"）：

```
        被调度选中                 时间片用完/被抢占
就绪态 ─────────────→ 运行态 ─────────────────────→ 就绪态
  ↑                    │
  │ 事件发生(被唤醒)    │ 发起I/O、等锁(主动让出)
  │                    ↓
  └──────────────── 阻塞态
```

> ⚠️ **关键不对称**：阻塞态不能直接回运行态，必须先回就绪态排队。因为唤醒时 CPU 不一定空着。**任何进程想上 CPU，都必须先经过就绪态。**

### Linux 五态（`ps aux` / `top` 的 STAT 列）

| 码 | 名称 | 对应 | 说明 |
|----|------|------|------|
| **R** | Running / Runnable | 运行+就绪 | 正在跑或可跑 |
| **S** | Interruptible Sleep（可中断睡眠） | 阻塞 | 可被信号叫醒（绝大多数睡眠）；`Ctrl+C` 能打断 |
| **D** | Uninterruptible Sleep（不可中断睡眠） | 阻塞 | 等关键 I/O，**不响应任何信号**，`kill -9` 都杀不掉 |
| **T** | Stopped（停止） | — | 被暂停（如收到 SIGSTOP） |
| **Z** | Zombie（僵尸） | — | 已死、等回收 |

> 💡 **实战**：进程 `Ctrl+C` / `kill -9` 都杀不掉 → 大概率卡在 **D 状态**，在死等一个回不来的 I/O（NFS 网络存储断了、磁盘故障）。只能排查硬件/存储或重启。

## 4. 进程的死亡与回收：僵尸 & 孤儿

| | 僵尸进程 (Zombie) | 孤儿进程 (Orphan) |
|---|---|---|
| 定义 | 子**死**了 + 父**活着但没回收** | 父**死**了 + 子**还活着** |
| 状态 | 已退出，残骸暂留进程表 | 仍在运行 |
| 危害 | **占 PID / 进程表项**，堆积可耗尽 PID 导致无法创建新进程 | 无害 |
| 归宿 | 父进程调 `wait()`/`waitpid()` 才被回收(reap) | 被 **PID 1 (systemd)** 收养 |

**为什么要有僵尸？**
子进程退出时产生「成绩单」（退出码、是否被信号杀死等），父进程需靠它了解子进程死活。子进程不立刻彻底消失、保留残骸，就是为了**等父进程来"领成绩单"**（调 `wait()`）。父进程一领，内核才真正清除僵尸、释放 PID。

**孤儿为什么被 systemd 收养？**
孤儿将来死亡时，原父进程已不在，无人 `wait()` 它，就会变成**无人回收的僵尸**。systemd 收养它 = 承担将来回收的责任。
> 所以孤儿机制本质上是**防止僵尸堆积的安全网**。

**僵尸排查（实战）**：
```bash
# top 顶部摘要行直接有 zombie 计数
top

# 揪出僵尸：STAT 含 Z，CMD 显示 <defunct>
ps aux | awk '$8 ~ /Z/'
```
> ⚠️ **排查口诀：僵尸不可杀，要治它爹。** 僵尸已是死的，kill 它无意义。要顺着僵尸找父进程 PID(PPID)，修复/重启/杀掉父进程；父进程一死，僵尸变孤儿被 systemd 收养回收。

**对照记忆**：
- 子进程知道父进程 PID → `getppid()`（主动问内核；父死被收养后会返回 1）
- 父进程知道子进程 PID → `fork()` 的返回值（生时即得）

## 5. 进程的创建：fork + 写时复制(COW)

### fork() 的奇特行为

```c
pid_t pid = fork();        // 调用一次，返回两次
if (pid < 0) {
    // 出错，创建失败（返回 -1）
} else if (pid == 0) {
    // 【子进程】在跑（子进程拿到返回值 0）
} else {
    // 【父进程】在跑（pid 是子进程的 PID）
}
```

- **调一次返回两次**：因为 fork 把当前进程复制一份，父子都从 fork 后继续执行。
- **靠返回值区分父子**：父得子 PID(>0)，子得 0，出错 -1。

### fork + exec 模型

shell 执行命令 `ls` 的流程：
1. shell `fork()` 出子进程（此刻是 shell 内存的副本）
2. 子进程 `exec("ls")` —— **丢弃整个内存映像，换成 ls 的代码和数据**
3. 子进程变成 ls 在跑

> 这是 Linux 创建并运行新程序的**主流方式**。

### 写时复制 (Copy-On-Write, COW)

**问题**：fork 若老实拷贝父进程全部内存（如 500MB），但子进程紧接着 exec 会把内存整个丢弃 → 拷贝纯属浪费，且这是最高频场景。

**COW 思路**：「先别拷，等到真正要改的那一刻再拷。」

1. **fork 瞬间不拷贝任何内存**：父子页表都指向**同一份物理页**，且全部标记为**只读**。fork 因此极快极轻。
2. **若子进程紧接 exec**：内存映像被换掉，共享旧页一次都没碰 → **零拷贝**，完美避开浪费。
3. **若真要写某页**：只读页被写 → 触发**缺页/保护异常** → 内核只复制**被写的那一页**，写方改副本，另一方继续用原页。

> Copy-On-Write = 写的时候才复制；不写就永远共享，要写也只复制被写到的那一页。

**COW 的代价（trade-off，挑战题常考）**：
> COW 赌的是"大部分页 fork 后不会被写"。
> - **赌赢**（如 fork+exec）：收益巨大，成本趋近于零。
> - **赌输**（fork 后狂写大量内存页）：每写一页触发一次缺页异常，**异常处理开销（陷入内核、查页表、分配、复制、改页表项、返回）让它反而比直接一次性批量拷贝更慢**；还有**内存延迟爆发**风险——fork 时内存账面轻松，跑着跑着 COW 不断复制新页，物理内存突然吃紧甚至触发 OOM（如 Redis 持久化 fork 子进程时需关注）。

## 6. 进程调度：CFS

### 调度的核心矛盾

三个互相打架的目标：**响应快（交互性）、吞吐高（效率）、公平（不饿死）**。
- 偏响应 → 频繁打断去伺候交互进程 → 切换开销大、吞吐降。
- 偏吞吐 → 让计算进程少切换连续跑 → 交互进程卡顿。

### 关键分类

| 类型 | 特征 | 诉求 |
|------|------|------|
| **CPU 密集型 (CPU-bound)** | 埋头计算，很少阻塞 | 多给连续 CPU 时间 |
| **I/O 密集型 (I/O-bound)** | 大部分时间在等(I/O/键盘/网络)，用 CPU 短 | 一旦要用希望马上能用（常连着交互） |

**为什么调度器优待 I/O 密集型进程**（完整论证）：
> I/O 密集型进程"上 CPU 用一小下就主动阻塞让出"。
> - **代价小**：它本就用不了多少 CPU，优待它**不会饿死** CPU 密集型进程。
> - **收益大**：① 保证交互响应（敲键盘瞬间处理）；② 让它尽快发出下一个 I/O 请求，**让 I/O 设备别闲着、与 CPU 并行忙起来，整体吞吐反而更高**。
> 一笔"几乎无代价、却同时改善响应和吞吐"的买卖。

### CFS (Completely Fair Scheduler, 完全公平调度器)

**核心规则一句话**：**永远挑选 vruntime（虚拟运行时间）最小的进程来跑。**
- 用**红黑树**按 vruntime 排序所有就绪进程，最小的在最左，取出 O(log n)。
- 进程跑的时候 vruntime 增长；跑得越久涨越多，越容易被超过、被换下。

**一条规则，三个目标自动涌现**（CFS 的精妙）：
> CFS 没有任何一行代码写"请优待 I/O 型"，但复杂行为作为副产品自动涌现：
- **优待 I/O 型**：它们睡得多、没怎么跑、vruntime 小 → 醒来自动排在最左、被优先调度。✓
- **不饿死**：**不跑就不涨，不涨早晚变最小，最小必被调度** → 没人会被永久跳过；贪吃进程跑越多 vruntime 涨越快、迟早被换下。✓
- **公平**：长期看大家 vruntime 被拉到相近水平 → 宏观上 CPU 时间公平分配。✓

**vruntime 的"虚拟"在哪——编码优先级**：
> vruntime = 真实运行时间按优先级**加权**。**高优先级进程 vruntime 涨得慢**（显得"还没怎么跑"，更易保持最小、继续被调度 → 实际分到更多真实 CPU 时间）；低优先级涨得快。Linux 用 **nice 值**(-20~+19，越高越谦让、优先级越低、vruntime 涨越快)调节。

**min_vruntime——公平性的"地板"**（防作弊，挑战题）：
> 攻击设想：进程故意"频繁睡一下→醒来插队跑→再睡"，让 vruntime 始终很小，变相霸占 CPU；或睡很久攒下巨额 vruntime 赤字，醒来连续霸占。
> 防御：CFS 维护全局 **`min_vruntime`**（当前就绪进程 vruntime 的最小水位线，**单调递增**）。睡久的进程被唤醒重入就绪队列时，**vruntime 被修正为约 `min_vruntime` 减一个小补偿值**——
> - **不让它无限小**：钳在水位线附近，无法靠睡眠攒赤字来连续霸占。
> - **给一点点优势**：略小于运行中进程 → 醒来能被优先调度"一下"（保证交互响应），但仅一个时间片左右，跑完就乖乖排队。
> 给的是"一次性小优待"，不是"可累积大补偿"，攻击收益被死死限制。

### 实时调度（凌驾于 CFS 之上）

| 策略 | 行为 |
|------|------|
| **SCHED_FIFO**（先进先出） | 高优先级实时进程一旦运行，一直跑到自己主动让出或阻塞，不被同级/低级抢占。要确定性。 |
| **SCHED_RR**（轮转） | 类似 FIFO，但同优先级实时进程间按时间片轮转，避免独霸。 |

> ⚠️ **层级铁律**：只要有实时进程就绪，它**永远优先于**所有普通(CFS 管的)进程。CFS 的"公平"只在没有实时进程要跑时才生效。（刹车系统在等，不能跟它讲"公平排队"。）

# 第二部分：内存管理

## 7. 虚拟内存：一个精心编织的谎言

**反直觉现象**：同一程序的两个进程，打印出的变量地址可能**完全相同**，却互不干扰。

**谜底**：进程看到的地址**全是假的**——**虚拟地址**。

- 每个进程活在幻觉里：以为独占一整片从 0 开始、连续、巨大的内存（**虚拟地址空间**）。
- 物理内存（内存条）是真实、唯一、所有进程共享的。
- 虚拟地址要真正读写，必须被**翻译**成**物理地址**。两进程相同的虚拟地址被翻译到不同物理位置，故互不干扰。

**虚拟内存的三大好处（存在理由）**：
1. **隔离与安全**：A 的虚拟地址只翻译到 A 自己的物理页，**A 无能力访问 B 的内存**（翻译表里没这条路）。野指针只能祸害自己。
2. **简洁幻觉**：程序员只管用自己干净、连续、从 0 开始的虚拟空间，撞车问题交给翻译层。
3. **物理内存可"超卖"**：承诺一大片虚拟空间但物理内存先不真给（**惰性**），用到才分配；暂不用的页可挪到磁盘(swap)。16GB 物理内存能支撑远超 16GB 的虚拟内存总和。

## 8. 页表与多级页表

**基础概念**：
- **页 (page)**：虚拟内存切成的固定块，Linux 通常 **4KB**。
- **页框 (page frame)**：物理内存切成的同样大小的块。
- 映射以"页"为单位：一个虚拟页 → 一个物理页框。
- **页表 (Page Table)**：存"虚拟页 → 物理页框"映射的表。

**页表是每进程一份，还是全系统共用？→ 每进程一份。**
> 推理：虚拟内存第一大好处是隔离 → 同一虚拟地址在 A、B 必须翻译到不同物理页 → 只有"各有一张不同对照表"才可能 → 每进程必须有独立页表。
> （这也解释了第 2 节进程切换为何要换页表：从 A 的页表换成 B 的；线程共享地址空间 = 共享同一张页表，故不换。）

**平坦页表为什么不可行（512GB 灾难）**：
> 64 位虚拟地址空间约 2⁴⁸，页 4KB(2¹²) → 虚拟页数 = 2⁴⁸/2¹² = **2³⁶ 个**（约 680 亿）。
> 每条记录 8 字节(=2³)：一张平坦表 = 2³⁶ × 2³ = **2³⁹ 字节 = 512 GB**（1GB=2³⁰，2³⁹/2³⁰=2⁹=512）。
> 16GB 物理内存放不下，且**每进程都要一份**，彻底荒谬。

> 💡 **底层算量技巧**：内存世界一切皆 2 的幂（页 2¹²、GB 2³⁰）。全化成 2 的幂后，乘法→指数相加，除法→指数相减，口算即得。做性能测试算内存/吞吐量同样适用。

**多级页表 (Multi-level Page Table)——树状 + 惰性**：

```
顶级表(树根) ──→ 二级表 ──→ 三级表 ──→ 末级表(叶) ──→ 物理页框
   只少数项      指向下级    指向下级    存真实映射
        │
        └─ 某区域从没被用 → 整棵子树压根不创建（顶级表对应项标记无效）
```

- 类比书的分层目录：章→节→页；没写的章节，目录里连提都不提。
- x86-64 通常 **4 级**，每级表一页(4KB)装得下。
- **惰性体现**：没用到的虚拟区域，整棵子树不创建，一字节下级表都不占。
- 成本从"必存 512GB" → "只为实际用到的几万页创建沿途小表"（几十 KB ~ 几 MB）。
- **本质：时间换空间**——用"多查几层"换"只存用到的部分"。

## 9. TLB：救回多级页表的速度

**问题**：4 级页表翻译一个地址要 **4 次访存**（逐级查），每次内存访问背后藏 4 次查表，慢到无法接受。

**TLB (Translation Lookaside Buffer)**：CPU 内一块极小极快的缓存，缓存最近用过的"虚拟页→物理页框"翻译结果。

翻译流程：
1. 先查 **TLB**。
2. **命中**：直接拿物理页框，**0 次查页表**，飞快。
3. **未命中**：走 4 级页表翻译，结果**顺便存进 TLB**，下次就快。

> 因程序访问内存有**局部性**（反复访问相邻/相同的页），TLB 命中率极高(常 99%+)，昂贵的 4 级查找绝大多数被省掉。

**闭环第 2 节的进程切换开销**：
> 进程切换 → 换页表 → MMU 指向新页表树根(换 CR3) → **TLB 整个作废**（新进程同一虚拟地址映射到不同物理页，旧翻译一条不能用）→ 新进程刚跑时频繁 TLB 未命中、要走 4 级慢翻译，直到 TLB 被新进程映射焐热。线程切换共享页表 → 不换 → TLB 不失效，故"轻"。

## 10. 缺页中断 (Page Fault)

**触发**：进程访问的虚拟页在页表里无对应物理页框（页表项无效）→ CPU"扑空"→ 触发缺页中断，交控制权给内核。

> ⚠️ **缺页中断是中性机制，不一定是错误**——它是惰性分配能运转的关键齿轮，意思是"这页现在没就绪，内核请介入"。

**内核接手后做权限检查，分两个相反结局**：

| | 情况 A：合法扑空 | 情况 B：非法扑空 |
|---|---|---|
| 含义 | 进程有权访问，只是物理内存还没分配（惰性） | 进程无权访问（野指针/空指针解引用/数组越界） |
| 处置 | **悄悄补上物理内存，程序无感继续跑** | 发 **SIGSEGV** 信号，进程被杀 |
| 现象 | 程序正常运行 | 终端打印 **`Segmentation fault (core dumped)`** |

> 💡 **段错误的真相**：野指针 → CPU 翻译扑空 → 缺页中断 → 内核查权限发现非法 → SIGSEGV → 进程被杀。segfault 不是玄学，正是缺页中断走到"情况 B 分支"的结局。

**情况 A 的两种细分**：
1. **首次访问，惰性分配（最常见）**：申请内存时只在页表"挂个名"标记合法，没真给物理页；首次写时扑空→缺页中断→内核才分配真实页框填入页表→重执行指令。程序无感。
2. **页被换回 (swap in)**：物理内存不够时不用的页被挪到磁盘(swap)，页表项标记"在磁盘"。再次访问→扑空→缺页中断→**从磁盘读回物理内存**→更新页表。
   > ⚠️ 这种要读磁盘，**慢**！内存吃紧疯狂 swap 会导致系统卡顿无比——大量缺页都在等磁盘 I/O，这叫 **thrashing(抖动)**。

## 11. malloc 的真相：VSZ vs RSS

**颠覆认知**：`char *p = malloc(1GB);` 成功返回时，**物理内存一个字节都还没给你**。

> malloc 拿到的是**虚拟地址空间**——内核只在虚拟地址空间划出一片标记"合法"的 1GB 区间并返回起始虚拟地址。物理内存等你**真正去写某一页**时，才一页(4KB)一页地通过缺页中断分配。写了 10MB 就只有 10MB 物理内存被真正划走。

| 指标 | 含义 | malloc(1GB) 后 |
|------|------|----------------|
| **VSZ (Virtual Size)** | 进程**申请**的虚拟地址空间总量 | 立刻 +1GB |
| **RSS (Resident Set Size)** | 进程**真正占用**的物理内存（实际写过的页） | 只随实际写入增长 |

> 💡 **测开实战**：`ps aux` 的 VSZ、RSS 两列。**VSZ 往往远大于 RSS**（申请的总比实际用的多）。监控被测服务内存、判断会不会撑爆机器，要盯 **RSS**，盯错 VSZ 会得出完全错误的结论。

## 12. OOM Killer

**绝境**：超卖超过头——内核乐观答应的虚拟内存总和远超物理内存+swap。某刻进程纷纷真正写入兑现"欠条"，物理内存+swap 耗尽，新缺页中断要兑现下一页却一页都没有了。

**OOM (Out Of Memory)**：内存耗尽（物理+swap 都用光）。
> ⚠️ 与编程里的"内存溢出 / buffer overflow(缓冲区溢出，写越界)"是**完全不同的两回事**，别混。

**OOM Killer（内存不足杀手）**：内核断臂求生——**主动挑一个进程杀掉，释放内存让系统活下去**。

**杀谁？按 `oom_score` 打分，挑分最高的**：
- **占用物理内存越多分越高**（杀它释放最多内存，性价比最高，主因）。
- 可通过 **`oom_score_adj`** 保护(调负)或献祭关键进程。
- 内核尽量避开关键系统进程（不会杀 PID 1 systemd）。

> 💡 **测开排查口诀**：**服务进程无声无息消失、无 crash 日志 → 第一反应查 `dmesg` / `/var/log/syslog`**，看有没有 `Out of memory: Killed process xxx`。压测把服务内存压爆、被测进程被 OOM 干掉，是性能/稳定性测试的高频故障场景。

**完整因果链（malloc → OOM）**：
```
malloc 超卖(只给虚拟、乐观都答应)
  → 进程真去写 → 缺页中断 → 内核兑现物理内存
  → 大家都来兑现 → 物理内存+swap 耗尽
  → 新缺页中断无法兑现
  → OOM Killer 出动 → 按 oom_score 挑内存大户杀掉
  → 释放内存，系统续命
```
> "超卖"(第7节乐观承诺)与"OOM"(残酷兜底)是同一枚硬币的两面：正因敢乐观超卖(提高利用率)，才需 OOM Killer 兜住翻车的极端情况。

# 第三部分：高频面试题 + 参考答案

> 答案采用「总-分-例」结构：先一句话总述 → 展开要点 → 举例/落地。

### Q1. 进程和线程的区别？为什么进程切换比线程切换开销大？

**总**：进程是资源分配的基本单位，线程是 CPU 调度的基本单位；同一进程的多个线程共享地址空间。进程切换更贵的根本原因是它要切换页表并导致 TLB 失效。

**分**：
- 进程有独立的虚拟地址空间(独立页表)、独立资源；线程共享所属进程的地址空间、打开的文件等，只独享寄存器、栈、PC。
- 两者切换都要保存/恢复寄存器、PC（开销相同）。
- 进程切换额外要：① 切换整套页表（MMU 指向新页表树根，x86 换 CR3）；② **TLB 失效**——旧进程缓存的虚拟→物理翻译全作废，新进程刚跑时频繁未命中、要走多级页表慢翻译。
- 线程切换共享同一张页表，不换页表、TLB 不失效，故轻。

**例**：Python 里 `multiprocessing` 起多进程开销和隔离都大，`threading` 起线程切换轻但受 GIL 限制；这正对应"进程重、线程轻"的底层差异。

---

### Q2. 什么是僵尸进程？什么是孤儿进程？怎么处理僵尸进程堆积？

**总**：僵尸是"子已死、父没回收"，危害是占 PID；孤儿是"父已死、子还活着"，被 systemd 收养，无害。

**分**：
- **僵尸**：子进程退出后保留残骸(退出状态)在进程表，等父进程调 `wait()`/`waitpid()` 回收(reap)。设计目的是让父进程能读取子进程的退出码等"成绩单"。父进程不回收会堆积，占满 PID 导致无法创建新进程。
- **孤儿**：父进程先退出，子进程被 PID 1(systemd)收养，由其负责将来回收——本质是防止孤儿死后变成无人回收的僵尸的安全网。
- **处理僵尸**：`kill` 僵尸本身无效(它已死)。要找到其父进程(PPID)，修复代码使其 `wait()`，或重启/杀掉父进程；父进程一死，僵尸变孤儿被 systemd 回收。

**例**：`ps aux | awk '$8 ~ /Z/'` 找出 STAT 含 Z、CMD 显示 `<defunct>` 的僵尸；`top` 顶部摘要行直接有 zombie 计数。

---

### Q3. 一个进程 `kill -9` 都杀不掉，可能是什么原因？

**总**：大概率它处于 **D 状态（不可中断睡眠）**，在等一个回不来的底层 I/O。

**分**：
- D 状态进程在等关键 I/O（通常是硬件级），此过程绝不能被打断（打断可能损坏数据/硬件状态），因此**不响应任何信号**，连 SIGKILL(`kill -9`)也无效。
- 常见诱因：NFS 网络存储断连、磁盘故障，进程死等永远回不来的 I/O。
- 处置：排查并恢复底层 I/O（存储/硬件），或重启机器；无法通过信号强杀。

**例**：`ps aux` 看到目标进程 STAT 为 `D`，且关联挂载点是已断开的 NFS，基本可锁定。

---

### Q4. 解释 fork() 和写时复制(COW)。COW 一定更高效吗？

**总**：fork 复制进程(一次调用两次返回)，COW 让 fork 时不真拷贝内存、写时才按页复制；它在 fork+exec 场景近乎零成本，但在 fork 后大量写入时反而可能更慢。

**分**：
- fork 返回两次：父得子 PID，子得 0，出错 -1。
- COW：fork 时父子共享同一批物理页且标记只读，故 fork 极快；任一方写某页 → 触发保护异常 → 内核只复制被写的那一页。
- **不一定更高效**：COW 赌"大部分页 fork 后不被写"。fork+exec 时旧页根本没碰，零拷贝(赌赢)；但若 fork 后狂写大量页，每页触发缺页异常，异常处理开销使总成本反超直接批量拷贝(赌输)，还有内存延迟爆发风险。

**例**：Redis 做 RDB 持久化时 fork 子进程，依赖 COW 避免立即翻倍内存；但若主进程此时大量写，COW 不断复制脏页，内存可能骤增甚至触发 OOM——这是 Redis 运维需关注的点。

---

### Q5. CFS 调度器的核心思想是什么？它如何做到既公平又不饿死进程？

**总**：CFS 仅用一条规则——总是挑 vruntime(虚拟运行时间)最小的进程跑——就自动实现了优待 I/O 型、公平、不饿死。

**分**：
- vruntime = 真实运行时间按优先级加权；高优先级涨得慢、低优先级涨得快(nice 值调节)。
- 用红黑树按 vruntime 排序，取最左(最小)O(log n)。
- **不饿死**：进程不跑 vruntime 就不涨，长期不跑早晚变全场最小、必被选中；贪吃进程跑越多涨越快、迟早被换下。
- **优待 I/O 型**：它们睡得多、vruntime 小，醒来自动被优先调度。
- **防作弊**：`min_vruntime`(单调递增水位线)兜底，睡久的进程唤醒时 vruntime 被钳到水位线附近，只给一次性小优待，无法靠睡眠攒赤字霸占 CPU。

**例**：编辑器(I/O 型)与后台编译(CPU 型)并存时，你敲键盘编辑器立即响应(vruntime 小被优先)，编译在空隙继续推进，两者都不卡死——这就是 CFS 的"公平"。

---

### Q6. 什么是虚拟内存？它解决了什么问题？

**总**：虚拟内存给每个进程一片"独占的假地址空间"，通过页表翻译成物理地址，解决了隔离、编程简洁、内存超卖三大问题。

**分**：
- 进程用的是虚拟地址，经页表(MMU)翻译成物理地址；不同进程相同虚拟地址映射到不同物理页。
- **隔离安全**：进程无法访问其他进程物理内存，野指针只祸害自己。
- **简洁幻觉**：程序员只管用连续、从 0 开始的虚拟空间，无需关心物理布局/撞车。
- **超卖**：承诺虚拟空间但物理内存惰性分配、用到才给，暂不用的页可换到 swap，物理内存能支撑远超其容量的虚拟内存总和。

**例**：同一程序跑两个实例打印出相同变量地址却互不干扰，正是因为这是虚拟地址、被翻译到了不同物理位置。

---

### Q7. 为什么用多级页表？平坦页表有什么问题？

**总**：平坦页表单进程就要约 512GB、且每进程一份，完全不可行；多级页表用树状结构 + 惰性，只为实际用到的页创建沿途小表，把成本降到几 MB。

**分**：
- 平坦表：64 位下虚拟页约 2³⁶ 个，每条 8 字节 → 2³⁹ 字节 = 512GB，物理内存放不下，每进程还要一份。
- 多级页表(x86-64 通常 4 级)：顶级表指向下级表，逐级展开，末级才存真实映射。
- 惰性：从没用到的虚拟区域，整棵子树不创建，不占空间。
- 代价：翻译要逐级查(4 级=4 次访存)——用 TLB 缓存翻译结果救回速度(命中则 0 次查表)。

**例**：一个用几十 MB 内存的进程，多级页表实际可能只占几十 KB ~ 几 MB，对比平坦表的 512GB，这就是"只存用到的部分"的威力。

---

### Q8. 程序报 "Segmentation fault" 的底层原理是什么？

**总**：段错误是缺页中断走到"非法访问"分支的结果——进程访问了无权访问的虚拟地址，内核发 SIGSEGV 杀掉它。

**分**：
- 进程访问某虚拟地址 → CPU 经页表翻译，发现页表项无效 → 扑空，触发缺页中断 → 内核接手。
- 内核做权限检查：若地址不在进程合法内存区域(野指针、空指针解引用、数组越界) → 判定非法 → 发 SIGSEGV → 进程默认被杀，终端打印 `Segmentation fault (core dumped)`。
- 缺页中断本身中性：合法则悄悄补内存继续跑，非法才 segfault。

**例**：C 里 `int *p = NULL; *p = 1;` 解引用空指针，触发缺页中断→权限检查非法→SIGSEGV→段错误。

---

### Q9. malloc(1GB) 成功后，真的占用了 1GB 物理内存吗？VSZ 和 RSS 有什么区别？

**总**：不会。malloc 只给虚拟地址空间，物理内存等真正写入时才一页页按需分配；VSZ 是申请的虚拟量，RSS 是真正占用的物理量。

**分**：
- malloc 成功只表示内核在虚拟地址空间划出一片标记合法的区间并返回起始地址，物理内存一字节未给。
- 真正写某页时才触发缺页中断、分配 4KB 物理页(惰性分配)。
- **VSZ**(Virtual Size)：申请的虚拟地址空间总量，malloc 后立即增长。
- **RSS**(Resident Set Size)：实际写过、真正占用的物理内存。VSZ 通常远大于 RSS。

**例**：测开监控被测服务内存时，应盯 RSS 判断是否会撑爆物理内存；VSZ 高只代表预留多，不代表真吃了那么多内存。

---

### Q10. 什么是 OOM？OOM Killer 如何选择要杀的进程？线上进程突然消失怎么排查？

**总**：OOM 是物理内存+swap 耗尽；OOM Killer 主动杀掉一个进程释放内存以保全系统，按 oom_score 挑(通常杀内存占用最大的)。

**分**：
- 因超卖：答应的虚拟内存总和远超物理+swap，大家纷纷真正写入兑现时内存耗尽，新缺页无法兑现。
- OOM Killer 断臂求生：按 `oom_score` 打分，占物理内存越多分越高、越易被杀；可用 `oom_score_adj` 保护/献祭；避开关键系统进程。
- **排查**：服务进程无声无息消失、无 crash 日志时，查 `dmesg` 或 `/var/log/syslog`，找 `Out of memory: Killed process xxx`。
- 注意 OOM(内存耗尽) ≠ buffer overflow(缓冲区溢出/写越界)，是两回事。

**例**：压测时把被测服务内存压爆，进程被 OOM 杀掉、应用日志却没有异常栈，`dmesg` 里能看到 OOM Killer 的击杀记录——这是性能/稳定性测试的典型故障定位场景。
